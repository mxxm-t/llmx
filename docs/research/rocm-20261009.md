## Review of the earlier proposal, 2026-10-09

The earlier proposal was written on 2026-10-08 from main 5472fcf91.
It is research, not execution evidence. The combined plan takes its bounded
launch, decode, collective and attention probes, existing-interface inventory,
and the warning that width 2 needs more than faster communication. The size of
Vulkan illustrates coverage, not a line-count estimate of implementation time.

The budget was recalculated from the same-session 2026-10-06 STATUS table:
about 30-34 us per sum at width 4 and 15-18 at width 2, using the wrong-output
no-sum timing builds. The proposal's approximately 27 us figure pairs older
no-sum results with a later reference and remains a planning target only.
Fresh controls must precede a fixed decision threshold. The 269/1050 ms prompt
figures are full model attention totals; a small QK dot is a separate probe.

The primary [HRX README](https://github.com/ROCm/hrx-system), checked 2026-10-09,
confirms early-access alternative HIP infrastructure outside the official stack,
not gfx906 qualification or measured llmx launch savings. HIP graph replay comes
before a proposal for another runtime. The [LLVM target documentation](https://llvm.org/docs/AMDGPUUsage.html)
distinguishes exact and generic processors; compile gfx906 and inspect emitted
dot instructions rather than assume a generic code object has them. Runtime
support must still be qualified separately from compilation.

Two design corrections: size-based algorithm selection is legal when each path
preserves the same required arithmetic/order, and custom AR still launches work
even when graph replay removes per-sum host submission. The current Backend,
Collective, profile, loading and precision owners remain authoritative. Loading
and fit cannot wait for a final porting step, and no empty skeleton is a landed
milestone. RCCL evaluation stays in the combined plan. Direct packets, HRX,
runtime dependencies and early GPU probes were not implicitly authorized by this
review. The user subsequently authorized optional RCCL and the bounded early
probe on 2026-10-09, under the deployment conditions in ROCM. The existing
first-support rule covers recorded open speed cells;
complete-backend or phase-final claims still require their full matrix.

## mx: the closest applicable implementation

In `tp-allreduce.cu`, `k_broadcast_reduce` writes each input into the peers'
staging slots, fences, signals with system-scope release/acquire ordering and
reduces in member order. It reads its own contribution from the original input:
the source documents a gfx906 stale-self-slot failure. Flags use uncached
allocation; staging uses fine-grained allocation. Initialization checks peer
access, and fast peer-write eligibility on gfx906 depends on the HSA fine-grain
PCIe setting. The kernel name or a successful peer-enable call alone does not
prove this path safe on another architecture.

The two-phase path requires aligned slices. Its crossover varies with width
and staged versus standalone groups; the current code also admits larger
standalone width-4 messages at a smaller threshold than the old megabyte rule.
These are tuning results to remeasure, not constants for llmx to copy.

`ggml-cuda.cu` prepares all ranks before its split launch entry points.
It excludes a staging-copy path from fused launch because that copy would run
before the producer subgraph. Its RCCL path uses F32 for small messages and
converts larger messages to BF16, then back. Therefore an int8 matmul comparison
can still have different communication precision.

The same file's stage-transfer path uses grouped `ncclSend`/`ncclRecv` with
`ncclUint8`: these move bytes without changing arithmetic. On HIP these are RCCL
calls. The reduction's BF16 conversion is mx policy; RCCL can reduce F32, as the
small-message branch already does. Custom AR therefore does not make RCCL
redundant in mx. AMD's [RCCL overview](https://rocm.docs.amd.com/projects/rccl/en/latest/what-is-rccl.html)
documents topology-aware collectives and GPU send/receive across PCIe, xGMI and
network transports. This describes library capabilities, not qualification of
the test system's pinned version or a guarantee of llmx's required reduction ordering.

Plan correction after the dependency review: evaluate a backend-local hybrid,
custom AR for small decode messages and RCCL for eligible large reductions,
stage transfers and fallback. Measure F32 sums and test ordering, graph lifetime
and failures before adoption. Keep the HIP ordered-copy baseline as an oracle.
RCCL is unnecessary for a single GPU; avoiding it for all multi-GPU paths was
not justified by this source evidence. No dependency is added by this proposal.

The meta backend coordinates member dispatch and whole-token graphs, with
capture eligibility and fallback paths. This explains why a fast standalone
all-reduce is insufficient: rank launch skew and graph ownership are part of
the delivered performance. Existing llmx measurements in [TENSOR-SPLIT](../TENSOR-SPLIT.md)
show submission/synchronization dominating width-4 decode. They are historical
measurements, not measurements of a new HIP prototype.

Inference for llmx: test visibility first, then a complete token-like chain
with graphs and concurrent rank launch. Keep collective buffers and graph
lifetimes together below the model. Do not reproduce GGML's meta backend.

The compute side was also inspected: [quantized tiles](https://github.com/mxxm-t/mx-llama.cpp/blob/eefc4e7321c869496146697d63362f073941aed6/ggml/src/ggml-cuda/mmq.cuh),
the [repack interface](https://github.com/mxxm-t/mx-llama.cpp/blob/eefc4e7321c869496146697d63362f073941aed6/ggml/src/ggml-cuda/q8_repack/repack.cuh),
[attention selection](https://github.com/mxxm-t/mx-llama.cpp/blob/eefc4e7321c869496146697d63362f073941aed6/ggml/src/ggml-cuda/fattn.cu),
its vector kernel and the gated delta kernel. The repack interface stages partial
uploads before packing a complete tensor and can release scratch afterwards.
Dispatch distinguishes vector, tiled and matrix-instruction attention according
to hardware and shape. Its small-row and prompt paths are different families;
a backend consisting only of a generic matmul misses that design. Some vector
attention builds use half intermediates, so a speed comparison needs the actual
selected precision, not only the weight file and cache label. llmx's own F32
attention-sum contract remains authoritative.

## vLLM: eligibility and executed policy matter

The standard custom AR owner rejects unsupported group sizes and groups of
more than two devices without the required full connectivity. Its registered
buffers and capture registration connect the communicator's allocation lifetime
to graph use. On the pinned ROCm platform, `use_custom_allreduce` enables that
route for gfx94/gfx95, not gfx906 or gfx1151. This is a policy of that route,
not a universal statement about every AITER or QuickReduce implementation.

The communicator has several candidates and a library fallback. Batch-invariant
mode excludes paths that do not promise fixed reduction order, including its
AITER and QuickReduce choices. The lesson is to qualify the exact selected path;
an enabled custom-AR flag is not a correctness or performance witness.

The ROCm platform also selects attention implementations by model requirements,
hardware, package availability and overrides. AITER/Triton/FlashAttention are
separate implementation families, not evidence that one kernel handles all AMD
generations. The transferable design is a small capability-based selector and
explicit unsupported cases. llmx implements its own paged-attention family and
does not inherit that Python/package selection stack.

AMD's [QuickReduce report](https://rocm.blogs.amd.com/artificial-intelligence/quick-reduce/README.html)
also describes optional integer communication formats. Its speed claim is not
a lossless F32 result for MI50. llmx's initial collective keeps F32 data and
fixed ordering; compressed communication is a separate numerical feature.

## SGLang and AITER: determinism and graph shape ownership

SGLang's ROCm selector normally chooses AITER when installed/enabled, but chooses
its own deterministic implementation for the one-stage deterministic mode. The
HIP deterministic wrapper explicitly invokes a one-stage reduction. Its tested
rank specializations are not evidence for llmx's required odd widths.

The decode graph runner owns bounded captured batch shapes, stable buffers,
padding and replay metadata. llmx already owns passes and row classes; retain
those semantics while the backend captures executable work. Do not introduce
a second frontend graph-shape scheduler or let padding change an entry's bits.

AITER separates architecture/transport choices and communication kernels in
their owners; its current sources also contain newer-architecture and prototype
paths. Source availability is not validation on MI50 or Strix Halo. Only use a
mechanism after its memory assumptions and arithmetic order are tested locally.

## Megatron Core: reuse the dependency structure, not the training runtime

`ColumnParallelLinear` can retain partitioned output; `RowParallelLinear`
reduces partial outputs before the replicated result is used. This is the
expansion/contraction split llmx's tensor plan already expresses. Sequence
parallelism takes a different reduce-scatter path; training gradient overlap
has its own dependencies and configuration.

Consequently the useful inference lesson is where communication is necessary
and where independent work can overlap. It does not justify adding training
abstractions or deferring a sum past a nonlinear operation that needs it.
The current configuration also distinguishes inference graph ownership from
training graph scopes. There should likewise be one graph owner in llmx.
The [parallel-layer API](https://docs.nvidia.com/megatron-core/developer-guide/latest/apidocs/core/core.tensor_parallel.layers.html)
documents these primitives; the source pin above is the reproducible reference.

## Research limits

The source comparison made no new GPU runs, profiling or speed claims. The foreign-source reads
focus on communication, graph lifetime, parallel-layer dependencies and device
selection, not exhaustive audits of those projects. Three obsolete SGLang
source paths returned 404; its pinned tree supplied the replacement paths listed
above. Original failures and fetched-source hashes remain in the local manifests.
Strix Halo is planned without available hardware. The next useful evidence is
the bounded HIP visibility/launch probe in ROCM step 1, now explicitly authorized
ahead of the remaining Vulkan tensor-split work.

The subsequent launch-only smoke is recorded in [STATUS](../STATUS.md): HIP
eager, HIP graph and Vulkan each produce the exact expected values on one MI50.
It does not qualify peer visibility, collective arithmetic, RCCL or performance.
The separate peer-memory probe also compiles for gfx906 and gfx1151 with
warnings as errors in that pinned image. Subsequent runs on two, three and four MI50s
pass all three public allocation modes with host-synchronized ordered sums:
432 exact epochs in total, recorded in STATUS. Those host-synchronized runs
do not qualify device-side synchronization, graphs, RCCL or performance.
The pinned image's RCCL 2.27.7 header/library and installed package versions
were then located under `/usr/local`; a library load and `ncclGetVersion`
succeeded without GPU access. The inventory and hashes are retained alongside
the probe. No communicator or collective was run by this inventory.
The later finite-payload RCCL screen, also recorded in STATUS, runs send/receive
plus ordered local sums successfully at two, three and four MI50s. Native F32
all-reduce passes the same inputs at two members and fails the member-order
criterion at three and four. All failed arithmetic cells are retained; no
performance, graph or failure-recovery qualification follows from this screen.

The later device-signal probe implements the mx protocol's relevant constraints
independently: system release/acquire epochs, all-writer system fences, original
local input and a consumed barrier before staging reuse. It checks every
consumed peer contribution as well as the ordered sum. With one block per member
and uncached signals, uncached payloads pass 512 epochs each at widths two, three
and four without the HSA fine-grain override. Fine-grained and ordinary payloads
fail on stale data under that same compiler/binary; all six failures remain.
The emitted gfx906 payload loads lack a cache-bypassing modifier despite the
source non-temporal hint, so the hint alone is not an instruction witness.
This narrows the next probe to uncached staging, without declaring every public
fine-grained protocol invalid or assigning a cause not isolated by the test.
Two omitted-member controls exit through the finite wait bound and drain.
At that checkpoint, graphs, multi-block residency, realistic sizes, general
failure recovery and performance remained unqualified. Source/binary hashes, emitted resource counts,
retained compile attempts and all eleven raw run records are listed in STATUS.

The subsequent bounded graph probe in STATUS checks multiple blocks, one
collective per kernel and captured chains over changing data and sequence
descriptors. Eager and replay pass the same independent exact oracle at widths
two, three and four; capture leaves initialized storage unchanged. Omitted
members time out, and repeated stale epochs are refused before new writes.
These checks cover the probe's ownership and finite inputs, not a model graph
cache, arbitrary dynamic shapes, general recovery or matched performance.

The lean follow-up removes saved intermediate contributions and the helper's
descriptor copy, and performs residual plus ordered member sum in place.
All 480 normal 32-kernel chains match the independent oracle at their final
residuals; all four negative controls pass. Emitted scratch drops from 72 bytes
to zero on both compiled targets. This is a combined code change and a
correctness result, not isolated attribution or a measured speedup; fresh
matched timing was the next step. Original probe artifacts remain intact.

The subsequent common-image Vulkan/HIP timing matrix in STATUS checks all
1,440 measured and 216 warmup chains. Its large microbenchmark advantage is
scoped to those operations and does not close mx or model gates. Width four's
small graph-sum block medians are 23.87 and 48.70 us; measured rank-start skew
rises from a median 7.78 us to 3,040.51 us in the slower block. This identifies
a host-launch delay to investigate, not its cause. The subsequent same-binary
host-wait comparison checks all 400 measured and 60 warmup chains. Enqueueing
every rank before waiting gives small graph-sum block medians 23.52/23.57 us
against per-rank waiting's 23.77/30.61 us; mixed eager chains still vary. This
supports that ownership for the next probes without explaining every delay.
Fresh mx controls, conservative HIP/RCCL paths and the model budget remain.
