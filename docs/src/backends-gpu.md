# `src/backends/gpu/` - the GPU backends' shared core and kernels

The host core and kernels a GPU backend over a vendor runtime is built from ([ROCM](../ROCM.md)): one class template over the vendor's `Api`, its calls static functions, so no call is virtual, and kernel sources every vendor compiles; the ROCm backend ([backends-rocm](backends-rocm.md)) instantiates them over HIP, with the ops of the text architectures (`implements`) and the weight types of `kTypes`, on one device, over a layer split and in tensor groups; what remains of that plan is listed there (Scope on main, 2026-11-05).

- `gpu_backend.hpp`: what the core shows a vendor's public header, the forms of a tensor group's fast sum (`GpuSumForm`), which the tests name.
- `backend_core.hpp`: the backend (`GpuBackend<Api>`), with its buffers, graves and KV storage, each a template over `Api`: the vendor's types (stream, event, module, function, device) and its calls as static functions, which a vendor's translation unit supplies and instantiates once (`rocm/rocm_backend.cpp`, `HipApi`); a failed call reports the vendor's name and the call's (`Api::check`).
  - Execution: one non-blocking HIP stream a device, every op an asynchronous launch on it.
  - Identity: `identity()` is the backend's name, the device's name and architecture and the driver or runtime version (`rocm gfx906...; HIP N`), and not the index or PCI address, since cards of one device and driver give the same bits; a kept disk cache is therefore adopted whichever card a tensor group's timed pick puts each member on (docs/DISK-TIER.md, The entry file). Messages name a card by `ordinal()`, `rocm:N` or `cuda:N`.
  - Records: a kernel launch (its function, grid and packed arguments, `Args`), a copy, a zero fill, or a handoff's wait for or write of a 64-bit word (`hold_wait`, `hold_write`) is held in the backend's record and issued in order at a flush, which first makes the device the thread's current one, since HIP finds a module's function through it and another backend's call may have changed it. A flush comes every `dispatch_chunk` held operations (the profile's), after the first 8 where the submission opened with nothing running on the device, at every submission and before every host wait that could cover held work (a dropped view of registered host memory, the destructor), and a tensor group flushes all its members before a sum and again once the sum's launches are held, so no member's sum kernel waits on a peer whose work the host still holds and the conservative path's events follow what they cover. A ring wrap submits only where the slot it takes next was read since the last submission, which no stage reaches, so a wrap is not a flush point and a stage's chunks follow its operations alone. A failure HIP reports as an operation is issued throws naming it, and the operations held after it are dropped.
  - Tickets: `submit()` records an event from a ring of 1024 and returns its ticket from the shared `TicketLedger` ([backend](backends-backend.md)), and a slot is reused only once its earlier ticket has retired. `wait` synchronises on the ticket's event and `done` queries it, but reads an event some thread is synchronising on as not done without asking HIP, which holds such a query until the work ends: the recording thread asks `done` as each submission opens, and a pipelined prefill's completion lane synchronises on the last stage's tickets (docs/STATUS.md, A ROCm ticket some thread synchronises on reads as not done).
    A backend made with diagnostics (`make_backend`'s, `bench --profile`) also records a timing event before and after each kernel, copy and zero fill it issues, the first 4096 of a reading interval, and `kernel_times` resolves them after the stream drains, kernels by name, the output head's (`matmul_logits`) with ` head` after it, the others as `copy` and `fill`; without diagnostics the flush records none.
    The ticket events are timing events, and a second ring of start events, one recorded before a submission's first operation that is not a wait on another device's word, gives `busy_ms` its time from there to the ticket event without waiting, -1 once a slot is reused.
  - Products into host memory (the logits): a product whose output is pinned host memory is formed in device memory and copied over whole, since the row kernel's one float a row over PCIe took the 0.6B's head 3.3 ms of a token.
  - Memory: `alloc` is device memory zero-filled on the stream, or pinned host memory the device reads in place (`Memory::host_visible`); `wrap_host` registers the caller's host memory with HIP, which registers an address once for every device, so the views of one memory on several devices (a head's tensor group's logits rows, the loader's read ring) count against one registration, and the last view dropped waits for its stream's copies and unregisters it at once rather than through the graves: HIP keys a registration by address, and one left behind after the caller freed its memory was taken for the next memory mapped there, whose copies faulted the device; HIP takes a second registration of a span and drops it at one unregister, so the count is the backend's, and a second span at a registered address, or one HIP refuses, gives no view, so the caller writes through staging; `copy` between two host memories, as a tensor group's head copies its member logits into the rows its members wrap, is `llmx_copy` on the stream through the device addresses HIP gives (`hipHostGetDevicePointer`), since HIP makes such a copy on the host once the stream has drained, which held the host about 7 ms a token on 2x2 (docs/STATUS.md, ROCm decode loop); `write` and `read` go through a pinned staging ring, and host values a kernel reads (positions, ids, block tables) through an argument ring, each slot reused once the ticket that last read it retires. The values every layer of a pass reads alike, attention's block table, firsts and ends, the KV write's blocks and slots and the positions, go through `pass_arg`: the first layer to name a set copies it from the argument ring into a ring of device memory on the stream ahead of its launch, and a later layer whose set has the same bytes reads that copy, so the kernels read device memory and not pinned host memory over PCIe; the host compares and never waits for the copy, and a device slot is taken again only once the last launch that read it retires. A dropped buffer's memory waits in the backend's graves until the work recorded before the drop is done, since `hipFree` unmaps it at once even while a queued launch or copy names it: a model buffer dropped mid-prefill faulted a 16K prompt. The graves are freed by a thread the backend owns, never by a thread that records or waits: once a grave's covering ticket is recorded the thread synchronises the stream and frees it, because `hipFree` and `hipHostFree` hold their caller until all the work queued on the device has run, which on a pipelined prefill's recording thread stopped its stage feeding the next, while a stream synchronise on another thread holds neither the launches nor the event queries of the thread that records (docs/STATUS.md, ROCm frees beside the devices); an allocation HIP refuses first waits for the graves under recorded tickets to be freed, which waits for the whole stream since the thread synchronises it, and is tried once more; it records nothing, so a drop since the last ticket is not counted. `memory_available` frees the recorded graves the same way before it reads, and `sync` records a ticket for drops since the last one, so a reading after `sync` counts every dropped buffer as free, as the fit needs.
  - Errors: a call refused as it is enqueued throws at once; a failure the device reports at an event is kept as the first cause, which `raise(t)` before results are read in place, `read` and the next launch or submission throw.
  - KV: blocks of 64 tokens through the shared `BlockKVStorage`, F32 or F16 sides, with a layer's auxiliary F32 rows and pooled-row room in their own plane of the same blocks (`kv_alloc`'s widths and pools), which `kv_write` fills token-major through the storage's copies (`write_aux`), an old buffer a growth copied from dropped into the graves like any other.
  - Weight types: one descriptor row a type (`kTypes`), naming the F32 class's exact product, the embedding and the type's twin kernels (`TwinKernels`: its row builds by form and columns, the output rows a wave of each takes, its four-row builds and its tiles, tall or not), which every caller reads, so no caller switches on a type; `supports_type` is that table. F32, F16, BF16, Q8_0, Q4_0, Q4_1, Q4_K, Q5_K, Q6_K, Q5_0, Q5_1, IQ4_NL, MXFP4, NVFP4, Q2_K, Q3_K, IQ4_XS, IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S, IQ1_S, IQ1_M, TQ1_0, TQ2_0, Q1_0 and Q2_0 are in it, and Q8_0, Q4_0, Q4_1, Q4_K, Q5_K, Q6_K, Q5_0, Q5_1, Q2_K, Q3_K, IQ4_NL, IQ4_XS, IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S, IQ1_S, IQ1_M, Q1_0, Q2_0, MXFP4 and NVFP4 have twins, IQ4_NL's grid values as signed bytes, sign-extended in the 16-bit words: BF16, TQ1_0 and TQ2_0 take their exact products in every class, wider than asked, as Vulkan takes its F32 rows, which `dtype_path` names from the table and the product records as the F32 path; F16 takes it in the F32 class and for generated rows, and outside the F32 class its prompt rows take the type's half tile (`TypeKernels::half`, `half_product`), recorded as the F16 path. `rocm_take_launches` gives the kernels launched since its last reading by name, the witness of which row build, tile or exact kernel ran. `rocm_profile` gives the profile the backend shapes its kernels by, which `kv-selection` reads and changes to run each selection form at one size, and `rocm_caps` the capabilities its rules read at each call, which `sparse_tile_pair` changes to take each few-row build.
  - NVFP4's exact kernels (`TypeKernels::scaled`) take the weight's F32 scales after the exact family's other arguments, one factor or one an expert a step apart, and run its F32 class.
    Its twins take one factor a projection (`RowCall::f`, `TileCall::f`) and apply it to each sum a kernel stores, a lane's partial in the row builds (`KFactor`, `k_out` in `kernels/int16.gpu`), so a weight with a factor an expert stays on the exact kernels in every class. `RowCall` keeps the first rows of projections 1 and 2 alone, projection 0 starting at row 0, so with the factors it stays at 128 bytes: at 136 bytes nvcc 12.9 gave `llmx_q6_k_rows16_8` 128 registers and 36 bytes of spill on sm_86 where 128 bytes give it 171 and none.
    `rq::NVFP4` (`kernels/quant.h`) decodes a value as `quant::dequantize_row_nvfp4` does, and `ExactNVFP4` (`kernels/f32.gpu`) rounds it again after the factor, as the CPU's `float_rows` does, so an embedding gives the CPU's rows and a product the F32 product of them.
  - F8_E4M3 has no twin; its kernels (`TypeKernels::scaled` is `Scaled::grid`) take the weight's scale grid and row shift, `check_grid` counting the grid against the call's matrices as the CPU's `fp8_scales` does, and routed calls the grid's step between experts.
    `rq::F8_E4M3` decodes a code as `quant::dequantize_row_f8_e4m3` does, and `ExactF8` rounds it once after its grid scale, as the CPU's embedding does, so a product is the F32 product of the embedded rows.
    Prompt rows outside the F32 class take `llmx_f8_e4m3_tile` (`kernels/int16.gpu`, `f8_tile`), the F16 tile's 64 by 64 with each code staged as its exact binary16 value and the activations rounded to binary16, as the CPU's f16 products round them: each 128-input partial is summed in F32 by half dots and added times its grid scale, as the CPU's `fp8_dot` adds it; decode columns keep the exact family, wider than asked.
    Its one-row and routed products take `f8_wave` (`kernels/f32.gpu`): four outputs a wave share each activation load in batches of four steps, and a code's bits placed as binary16 are its value / 256, so the scale times 256 rounds each product once as `ExactF8` does and each output keeps the bits of `exact_wave`; a scale from 2^119 up, a scale not finite or a word holding a NaN code takes `ExactF8`'s decode.
  - Ops: `matmul`, `matmul_add`, `matmul_group` (one twin for the group's projections, kept for the next product of the same activations in one of two twin slots, the newer first, a new twin taking the slot not holding the newer kept one and a twin a product reads becoming the newer, so the routed act's twin leaves the mixed streams' for the shared expert; a launch writing only an exact product's, a router's, a grouping's or a producer's outputs, or a copy, keeps both unless it writes a kept twin's input, `launch_writing` and `forget_written`, the one owner of forgetting them, while any other launch, a write or an allocation drops both; `group_rms_norm` writes four values and their twin a thread, in aligned 8-lane groups of a wave, where its operands lie on 16 bytes, and one a thread otherwise, the same bits either way) and through them `matmul_logits`, on the table's types: in the F32 class every type decoded exactly into F32 sums, in the F16 class Q8_0, the K-quants, Q5_0, Q5_1 and IQ4_NL on the block-int16 twin and in the int8 class on the block-int8 twin (`native_dtypes` {f16, f32, int8}, docs/PRECISION.md, section 5); `embed` of a table of any of them, at 64-bit offsets, and `embed_ids` through the same gather a type (`llmx_gather`, `llmx_gather_<type>`, which take the table's row count and write a +0 row for an id at or past it) with the ids read on the device, `argmax_rows` (`llmx_argmax_slices`, a block a slice of the profile's `argmax_slice` logits, then `llmx_argmax_merge` taking a row's slices in order on one lane, each step keeping the larger value, the lower id of equal values and a NaN or +inf flag, and refusing a row of no ids as Vulkan does), `gather_rows`, `rms_norm_rows`, `norm_rope_partial` over several rope streams, `gated_rms_norm`, `sigmoid_mul`, `causal_conv_silu`, `gated_delta_rule` (a block a view, V head and 32 V columns, in the Vulkan shader's order, so a sequence gives the same bits however its views are cut; the build staging 4 tokens where every view of the call holds at most 8 rows, as Vulkan chooses its short build, else the one staging 16), `norm_rope_kv`, `silu_mul`, `add`, `copy`, `kv_write`, `attention`, the Flash-Next stream and conv ops (`group_rms_norm`, `silu_scaled`, `mix_streams`, `inject_streams`, `signed_sqrt_gate`, `dilated_conv_silu_add`, in `kernels/f32.gpu` at their Vulkan kernels' op boundaries and orders, F32 outputs, each row from that row alone and the conv's view in chunks of at least its history, so only a view's first chunk reads and leaves its carried raw rows), and the routed experts (`Op::routed_experts`): `route_experts` (a row a block of 64, its reductions the 64-pair tree, in the Vulkan kernel's order), `matmul_experts` and `matmul_experts_add`, each entry through its type's one-column body over its expert's rows (`llmx_routed_<type>` in the F32 class, the twin types' `routed16`, `routed8` and `routed_half8` builds in the others, `routed_half8s1` on rows under two spans of blocks as the dense one-column build), so an entry gives the bits of its expert's one-column product; in the twin classes a call from its build's break-even (`TwinKernels::group_from`) groups them, but for a half-block call of at most one entry an expert on rows under two spans of blocks or from four, which takes the one-column build an entry and no grouping launch, since that build fills its one or four steps there and the grouped build's two steps are faster between, by expert (`llmx_moe_group`, the Vulkan grouping) and runs each group of up to 2, 4 or 8 entries, the narrowest holding their average, through the row build of that many columns (`routed16_g<C>`, `routed8_g<C>`, `routed_half8_g<C>`), a column an entry, whose twin column and outputs the build reads from the group (`EntryCols`), so each entry keeps its one-column bits and an expert's rows are read once a group; a prompt's rows from its build's tile extent for the call's role, gate and up or the down (`TwinKernels::tile_from`), take the routed tile instead (`routed_tile16`, `routed_tile8`): the grouping in groups of up to 64 entries, each group a block row of the prompt tile's 64 by 64 design over its expert's rows, or of its narrow build of 16 rows (`routed_narrow16`, `routed_narrow8`) where the group's entries fit them, both launched and each group running in one, never split, each entry's blocks summed in order in both, so an entry's sums are its own, the same in either build and within the tile's bound of its one-column product; and the down slots joined in slot order by `llmx_moe_combine`; `moe_step` is the base's sequence of them, or three fused launches where `fused_step` holds (Kernel notes, below); `delta_step` is the base's chain of the linear-attention ops, or the qkv and gate products and one fused launch where `delta_holds` holds (Kernel notes, below); and the indexer, `pool_kv` and `select_kv`, both pooling through one kernel (`llmx_kv_index_pool`), `select_kv` then scoring at most 16 rows at once (`llmx_kv_index_scores`) and selecting in one of two forms by the view's complete groups, the one-block selection (`llmx_kv_index_select`) below the profile's `select_wide_from` and from it the five-launch wide form over slices of 1024 groups (`llmx_kv_index_select_wide`), both by raw score bits with ties to the earlier group, so they give the same ids; and `sparse_attention`, each row over its selection slots, its group's ids each naming a power of two of positions (`slot_ids` and `slot_token`, `Op::sparse_attention_blocks`; one group of single positions is the ids themselves), through the per-row attention body's sparse build for heads 128 and 256 wide (`llmx_sparse_attention_vec`, `llmx_sparse_attention_vec256`, the dense body's template with its head width a parameter) split in chunks of 256 ids and merged in split order (`llmx_sparse_attention_vec_merge`, `_merge256`), and through the chunk body's sparse build for other widths (`llmx_sparse_attention_chunk`, `llmx_sparse_attention_merge`), chunked by the slots, so a row's splits follow the slots alone; an id outside the row's causal prefix is skipped and a row of none gives zeros; and DeepSeek-V4.1's ops (docs/DEEPSEEK4.md, section 4.2), a kernel each, `topk_rows` and `candidate_blocks` one (`llmx_topk_rows`, a block a row, the picks' least key found four bits a round from the top by a radix select over a histogram a wave in shared memory, the row read four keys a lane, and each pick's place ranked by wave ballots), `route_experts` under the sqrt_softplus rule its own, a wave a row with exact argmax picks by shuffles and the sum in pick order on one lane (`llmx_route_sqrt_softplus`), `hc_collapse_norm` writing its output's twin beside it where the row is whole blocks, as `rms_norm_rows` does, `norm_rope_partial`'s other forms their own (`llmx_norm_rope_form`) and `silu_mul`'s clamp and GLU form (silu, or MiniMax-M3.1's quick_gelu, `Op::glu_quick_gelu`, in the CPU's order) arguments of its kernels, the pooled-row ops reading the auxiliary plane through a table of each row's block ids and position (`pooled_table`), and `moe_step` the base's sequence for either rule and a clamp, and `mix_rows`, DSpark's tap, a block a row's run of columns summing its taps in order by fused multiply-adds, the CPU's bits (`llmx_mix_rows`), and the vision encoder's ops (docs/VISION.md, section 3): `layer_norm_rows` a block a row (`llmx_layer_norm_rows`), `gelu` in either form a thread an element (`llmx_gelu`), `add_bias` a block a row (`llmx_add_bias`), the rope over position streams `norm_rope_partial`'s `llmx_norm_rope_streams`, and `attention_full` the attention kernels' own non-causal views, a row's end the view's last key. Every other weight type and named op is refused at load (`supports_type`, `implements`), `mixed_experts` and `sigmoid_routing` among them, and `join` makes a tensor group's collective (`collective_core.hpp`, below).
  - Memory: `memory_available` is HIP's free device memory, and the fit leaves no share of it: `resident_bytes`, `scratch_bytes` and `allocation_bytes`, by which the fit counts each KV plane and state buffer, count each buffer at the pages hipMalloc takes, its units read at construction from the free memory 64 4-byte and four 1 MiB + 4 byte allocations take (`probe_memory`, `allocation_unit`, 2 MiB where a reading fits no power of two). The small unit is the sub-allocator's average over the 64, not a page (32 KiB on an MI50, whose small buffers share 2 MiB pages), which prices a buffer below 1 MiB as the runtime places many of them. Scratch: every scratch buffer's size for a call comes from one function its grow site and `scratch_sizes` share (attention and sparse parts, the sink's rows, the routed slots and groups, the fused step's twin, the tile split's partials over `split_partials_most`, the indexer's scores and state, argmax slices, the hyper-connection mix, both twin slots at the 16-bit class with each map region's padding, the host-bound head's staging), and `reserve_scratch` makes each at the widest call the widths allow. A call with any row on the per-row attention kernel prices all its rows at that kernel's split count, which is the kernel's layout, not a margin. `memory_kept(free)` ignores the fit's reading and is the runtime's private scratch for kernels that spill (the largest `HIP_FUNC_ATTRIBUTE_LOCAL_SIZE_BYTES` of any kernel times the lanes a compute unit holds and its compute units, none where no kernel spills) and a group's signal block; without the old 256 MiB and twentieth a server fitted to the whole card relies on these being exact, which the `backend-rocm-scratch` test holds.
  - Batch invariance: every kernel computes a row from that row alone in a fixed order. `row_class` makes a generated token one class; a prompt's rows are classed by the product tile's column tiles at their extent (`split_tiles_of`, up to 512 rows), which choose its inner split, by how many routed builds' tile extents (`TwinKernels::tile_from`) it reaches, which choose the routed tile, and by whether the extent reaches the profile's `attention_tile_rows`, which chooses the attention tile, so a choice follows the rows' prompt and never the rows a call holds.
- `collective_core.hpp`: a tensor group's collective (`GpuCollective`, docs/ROCM.md, step 4), which `backend_core.hpp` includes after the class; `join` takes two to sixteen devices of one backend and kind, each once, led by the backend it is called on.
  - Fast path, the one-shot: each member's `llmx_group_sum` kernel (`kernels/f32.gpu`), on that member's own stream behind the work that wrote its partial rows, writes them into its slot in every peer's area, uncached memory (`Api::malloc_uncached`, `hipExtMallocWithFlags` on ROCm) that a peer's stores reach without the fine-grain setting, and takes each peer's rows from its own slots as they land, with no flag and no meeting: a slot holds the signalling NaN 0x7f800001 (`kGroupArmed`) until its value arrives, a sender's value of those bits goes as its quiet twin 0x7fc00001, and a receiver spins on each unit of four floats (a float at a time in a tail) until none holds the armed bits, adds the members' rows in member order, its own from its partial rows unsanitized and the others' from its slots, as `sum_rows.comp` adds them (t = p0, t += p1, ..., then residual += t, or residual = t in place), and arms the slots it read again. Every value meets at least one add at a width of two or more, and an add quiets a signalling NaN, so the twin is invisible in the bytes, which `join`'s probe checks on every member; the bytes are the Vulkan collective's. The slots come in two parity halves, armed by `llmx_group_arm` at join: the host flips the half at each one-shot and passes it in the flags (4), the same for every member and block, so a member writes a half only once every peer has finished the sum before last, which it did before sending the last one's values, and two sums may be in flight on one collective. Up to 16 blocks, each member's `GroupPeers` written once at join into its own device memory and passed by address, so the launch's arguments do not grow with the width (`kGroupMembers`, the kernel's `GroupSignal` and `GroupPeers` sized by `backend::kMaxTensorWidth` and pinned by `static_assert`s on both sides). QDEV7's breakdown measured a 20 KB sum at 8.5 against 17.4 to 18.1 us over four MI50s of one root complex with the flag, fence and two meetings it replaced (docs/STATUS.md).
  - A generated row's sum in place on a group of two, of a width that is a multiple of 1280, runs the one-shot's halves apart: each member's `llmx_group_push` writes its rows into its peer's slot, and the member's backend holds the take as its pending join, which `llmx_hc_entry` finishes with the inject and mix after it, or `llmx_group_take` alone at the next operation; a flush that drops a held take sets the member's status word, so the next sum turns conservative.
  - Two other forms move a large sum's rows (TENSOR-SPLIT section 4.3), each adding every element as the one-shot does, `((p0 + p1) + ...) + p(W-1)` and then the residual, so every form gives the one-shot's bytes at any size and width for every value but a NaN made of two NaN inputs, whose payload may follow either input.
    Two shots: the units are cut into a share a member, whole units of four floats; every member pushes share k of its rows into member k's staging and meets, member k adds the share in member order into its own output and into every peer's own slot and meets again, and every member then adds the shares it gathered; 2 (W - 1) / W of the rows leave a card in place of W - 1, up to 32 blocks.
    The chain: member m adds its partial rows to the running sum member m - 1 passed into m's own slot and passes the result to m + 1, chunk by chunk (4096 units), and the last member's total flows back down through each member's slot m + 1, so the rows cross only between neighbours in member order.
    The wrap, the chain's kernel with flag 8, adds the same way and sends the total on around, W - 1 to 0 to 1 and on to W - 2 through each member's slot m - 1, so each card sends to one peer; every chunk still flows 0 to W - 1 unrotated and the total is formed once at member W - 1, so its bytes are the chain's, and at width 2 the two are the same route.
    In both, blocks [0, F) carry the sums ahead and [F, 2F) the totals back, F up to 16, chain block b takes chunks b, b + F, ..., and each chunk is told by a running count in the receiver's signal block (`ahead`, `back`) that every member's `passed` counts keep equal.
    Every form ends at a meeting, so a sum in any form may follow one in any other on the same collective; each takes the parity half the next one-shot takes, which every peer finished reading at the one-shot before the last, and a reader arms the one-shot's slots it read again before the last meeting, so the one-shot still finds them armed. Every form reads a peer's value as the one-shot does (`group_take`): it waits until no float of the unit holds the armed bits and arms the slot again once taken, so a meeting word or count that reaches a reader before its data, as PCIe relaxed ordering allows, delays the sum and never gives an earlier sum's values. Their meetings' epochs live in the signal block, one a block, and skip 0 on the 32-bit wrap, since fresh slots hold 0.
  - The form: a sum of n floats takes the form that won at the largest timed size not above n, the one-shot below them all. `join` times the forms on the group's own cards at its first collective of a size past what was timed for the group, its members idle: each form's least time over three sums in place after a first (`timed`), at the reserved rows and halvings of them, whole rows down to one so a generated row is a timed size, to where the one-shot wins or to 4096 floats, kept with the probe's answer by the first member and printed on stderr once a group and size (`rocm: tensor group of devices 0, 1, 2, 3 timed its sums in place, ms one-shot, two shots, chain, wrap: ...`), since which form wins follows the cards' places on the PCIe tree, which no device number gives; a launch that fails while timing leaves the group conservative, as a failed probe sum does.
  - The pick of groups and member order (`member_order`, docs/TENSOR-SPLIT.md, section 4.1): asked once a listing before any weight loads, it starts from the listing and runs one swap descent over every pair of devices, within a group or across two, a group costed as its fastest form at the pass's rows on a collective of its own, timed once for its members as ordered (`group_probe` first, quietly, skipped for a set whose probe failed), the peer access its probe enabled disabled again once it is timed, since a CUDA device holds at most eight peers, and enabled again (`group_access`) before another order of a set already probed is timed, a permutation as the sum of its groups, a swap taken only where the groups it changes beat those they replace by `kOrderMargin` (4%), and prints `rocm: tensor groups 0+1, 2+3 take devices 0+2, 1+3, ...` with both totals and `K groups timed in X ms`. Each picked group is then probed and reported as `join` reports it, and its forms are timed into its path as ordered, kept by its first member, so its `join` times nothing up to that size; every collective it timed is freed before the fit reads free memory, and the permutation is kept for the listing and width, so a second model on the same backends takes the same pick. A group of two kinds, or whose probe finds no peer writes, is never formed; a width of one, a listing not of whole groups or sums below 4096 floats keep the listing. `times_groups` says so, so the command line prints no grouping by PCI root for these backends. `rocm_collective` (`rocm_backend.hpp`) makes a collective whose fast sums all take one form, its members possibly backends of one device, for the tests; there is no flag.
  - Failure: a member waits for a late peer as long as it takes, since the host issues every member's sum together and each depends only on work issued before it, so an alive peer always comes. Its waits give up only when a peer set the area's abort word, when the host set the collective's cancel word, which it does where a member's launch of the sum throws, read once a millisecond of the device's wall clock (`hipDeviceAttributeWallClockRate`), or, in `join`'s probe alone, after one second of that clock, where peer writes that never become visible are what the probe looks for. The kernel then leaves NaN where its sum would be, leaving the slots it did not read unarmed, which no later fast sum reads, sets the abort word in every member's area, the collective's status word and its backend's fault word, both in pinned host memory. The fault word throws once at that backend's next check (`raise`, a launch or a submission), and the collective, which reads its status words in `wait` and before each sum, takes the conservative path for every later sum. A sum checks every member's failures before it launches on any, so no member waits for a peer whose launch threw. A live peer always arrives, since the host enqueues every member's sum in one order with no cycle, and a hung device hangs the sum, as the pull path and Vulkan's collective already do.
  - Host writes (`GroupTransport::host_writes`): where peer access is refused, as on a pair of GeForce cards without a bridge, each member's signal block and staging slots are pinned host memory every member maps (`host_malloc`, coherent) instead of its device memory, and the same kernels, forms, parity halves and armed bits run over them: writers store across PCIe, readers spin on their own slots in host memory. The signal blocks are zeroed by the host. Such a collective also times pulls (`GpuSumForm::pulls`) beside the four forms, the conservative path below copying into device memory of its own (`pull_`, with a `GroupPeers` table naming it) so the armed slots stay armed, and a size where pulls won takes them. `join` prints the pinned host memory such a collective holds, W areas of the signal block and 2W slots of the reserved rows, so a host's memory limit is seen.
  - Conservative path: each member records an event once its partial rows are written, pulls every peer's rows into its staging behind that peer's event, records a second event, and sums with the same kernel, in the same order, once every peer's second event says it has read its rows. It is taken from the start where both of `join`'s probes fail (`group_transport`: peer writes first, then host writes, which skip the peer access checks): a directed pair that cannot reach the other's memory, peer access refused, a member whose add tells a value from the twin the one-shot sends for the armed bits (`GpuCollective::add_check`: `llmx_group_add_check` adds 13 patterns, the armed bits, their twin, both signs of signalling and quiet NaNs with payloads, both infinities, both zeros, a denormal and a normal, as a + b, (a + b) + c and c + (a + b) raw and sanitized, read from memory the host wrote), or one fast sum of known rows that gives other values or gives up. It pulls into the first parity half.

The twins of the quantized products' activations are made here, at 32767 levels for block-int16 (`llmx_twin16`) or 127 for block-int8 (`llmx_twin8`), by the rule in STATUS, and, as the Vulkan producers write them, by `rms_norm_rows`, `silu_mul` and the per-row attention (at one split, else its merge, when no row of the call takes the tile) beside their outputs once a product has read a twin in that class, laid out from the runs they are given (the attention from its views) as the product of those runs lays it: the backend keeps the twin's tag, and a product of that output reads it instead of making its own, while any other launch, copy, write or allocation drops it. Norm rows of up to 8192 values take a block of 1024 threads that load the row and its weights at once and each scale and twin a quarter of what a 256-thread block's would, the sum chained by 256 of them in the plain kernel's order, which serves wider rows; a call of at most half as many rows as compute units cuts each row into parts of about 512 values in a second grid dimension, at most one block a compute unit, each part repeating the row's sum and writing only its share, so a decode row runs on several units with the bits of one block. Attention splits each row's history into chunks of its own, at 256 positions each and at most 16, each chunk an online softmax over 64-position tiles in order, then merges the chunks in order; the split depends on the history alone, so a row gives the same bits in any call. A prompt's view whose extent reaches the profile's `attention_tile_rows`, causal and of 128-wide heads, takes `llmx_attention_tile`, the Vulkan attention tile's design (`attention_tile.comp`): a block a tile of 32 query rows of one view and one head, eight lanes a row holding 16 dimensions of the scaled query, K and V through shared memory 16 tokens at a time, scores as partial dots folded by a butterfly over the row's lanes and a per-row online softmax over the row's whole history from token 0; a row depends on its own history alone. Generated rows and shorter prompts of 128-wide heads, and every row of 256-wide heads, take `llmx_attention_vec` (`llmx_attention_vec256` at 256, its split bounded by `attention_split_max_wide`), the Vulkan per-row attention's design (`attention_vec.comp`): a block a (row, head, split), 16 streams of 16 lanes each taking every 16th token of the split, a lane 8 dimensions, an online softmax per stream and the streams merged in order; a row's splits are chunks of its own length (the profile's `attention_split_chunk`, doubled until at most `attention_split_max` parts), so it computes the same beside any rows, and `llmx_attention_vec_merge` (`_merge256`) adds the splits in order. Other head widths keep the chunk kernel. `norm_rope_kv` is one launch a layer (`llmx_norm_rope_kv`): q's and k's heads normed and rotated in place by the device function `llmx_norm_rope` holds a head with, and k and v written into their KV blocks as `llmx_kv_write` writes them; a head wider than a block, or k's rows not dense, takes the ops one at a time. Every kernel skips a tile row, marked by an end of 0. The exact products and embeddings of the other types (`llmx_matmul_<type>`, `llmx_gather_<type>`) decode each value through `kernels/quant.h`, as the F32 product sums: an output's sum is 256 strided chains, lane l's over values l, l + 256 and so on in order, folded by the block tree. One row takes a wave an output (`exact_wave`), each lane holding 256 / warpSize of those chains side by side, so its loads are whole: F32, F16 and BF16 rows read four weights at once where they are aligned, and the steps every lane fills are unrolled so their loads issue ahead of the chains; the tree's levels from the wave's width up are shuffles and those below it adds in registers, the same pairs, so an output keeps the bits of the block an output it replaced; the routed F32 class's entries (`llmx_routed_<type>`) run the same body. An F32 call of two to four rows takes `llmx_matmul_cols2_f32` or `llmx_matmul_cols4_f32` (`exact_cols`), a wave an output that reads its weight row once and keeps each row's chains, so every output has the bits of its one-row product; a verify of three drafts would otherwise take the 8-row block for four rows. Any other call of more than one row takes `llmx_matmul_rows_<type>`, a block of 8 outputs by 8 rows whose lanes keep the same strided chain for each output and row and fold each by the same tree, so every output has the bits of its one-row product while a weight row is read once for 8 rows and an activation row once for 8 outputs. Sparse attention of heads 128 or 256 wide where the query heads a KV head serves are a multiple of four takes `llmx_sparse_attention_vec_g4` (`_vec256_g4`) where its groups give every compute unit one, the mirror of the Vulkan four-head build and its choice: a block a (row, four heads of one KV head, split), each selected token's keys and values loaded once for the four heads, each head with the per-row kernel's streams, chains and merge, so its output keeps that kernel's bits.

## Kernel notes

What the kernels' comments leave out, file by file and in file order: their layouts, their orders of work and why they take them.

`kernels/f32.gpu`:

- The dense F32 kernels of the ROCm backend (docs/ROCM.md, Delivery checkpoints, step 2) and the activation twins the quantized products read: every sum is F32 in a fixed order that depends on the row alone, never on how many rows a call holds.
  A block reduction folds lane partials in one tree whatever the wave width, so a row gives the same bits in any call.
- A block a row of n <= K * kThreads values: dst = RMSNorm(src) against w, with its twin at L levels beside it when L is not 0, the rows then dense and n a multiple of 32.
  Each of the block's kNormThreads threads loads its values and their weights at once, element t + kNormThreads j; the sum is rms_norm_row's, thread t < kThreads chaining elements t + kThreads k and the chains folded by block_sum's tree, so both give the same bits.
  A launch may cut each row into parts in blockIdx.y, whole 32-value blocks each; every part sums the whole row the same way and writes only its share, so the parts give the bits of one.
  The part count is a kernel argument, since reading gridDim.y adds hidden kernel arguments that cost every launch 1.4 to 2.9 us on an MI50.
- Member `rank`'s part of a group sum of n floats: out = the members' rows added in member order (flag 1), or out += them.
  Fast (flag 2), the one-shot: write its own rows, sanitized (`group_sane`), into its slot of every peer's parity half (flag 4), then take each peer's unit from its own slots once no float of it holds the armed bits, add in member order and arm the unit again (`group_take`); otherwise the host has pulled the peers' rows into its staging.
  A thread's wait gives up as `group_stop` says, looked at every 64 spins (`kGroupSpinChecks`), or once another thread of its block has; a sum that gave up leaves NaN in out.
  `llmx_group_two_shots` and `llmx_group_chain` take the same arguments for two shots and the chain and wrap (`group_two_shots`, `group_chain`, flag 8 the wrap), kernels of their own so the one-shot keeps its registers and a group of 16 ranks stays resident on one device (`LLMX_ONE_SHOT_BOUNDS` in port.h holds the one-shot at five waves a SIMD, which 16 ranks of 16 blocks need on a 60-compute-unit gfx906), each ending at a meeting after arming again the one-shot slots it read; every staging read in them goes through `group_take` and every raw row they send through `group_sane`, as in the one-shot; a chain block whose wait failed leaves NaN in every chunk it writes into out.
  `llmx_group_arm` arms a member's staging at join, and `llmx_group_add_check` is the probe's check of the add's NaN rule.
- A block a (row, head, chunk) of the split attention: 64 positions a tile, four threads a position's dot and one thread a dimension's accumulator, an online softmax over the chunk's tiles in order.
  The chunk's maximum, sum and accumulators go to `part` for llmx_attention_merge.
  SPARSE reads the row's `stride` selected ids in place of its positions, chunked by the stride alone, an id outside the row's causal prefix (`ends`) skipped.
- Causal attention of a prompt's rows (the Vulkan tile's design, attention_tile.comp), heads DIM wide, 128 or 256: a block a tile of 32 query rows of one view and one head (`llmx_attention_tile`, `llmx_attention_tile256`), eight lanes a row each holding DIM / 8 dimensions of its scaled query, K and V through shared memory TK tokens at a time, 16 at 128 wide and 8 at 256, so both widths take the same shared memory; the 256-wide build folds its running maximum, sum and accumulator into a total every 256 tokens, rescaling both by one `expf`, so no sum chain runs past 256 tokens and a row's bits stay a function of its own history, where an unfolded chain grew its error with the history's square root.
  The total's denominator is a two-float sum over the folds (a value and its rounding error, by exact products and sums), because its rounding scales every output of the row alike: in F32 alone it moved the mean signed error of `check_long` at 16384 tokens to -2.47e-8 of a double softmax on a T4 and a V100, past its 2e-8 bound; with the two-float total it is -1.22e-8 on both and -3.21e-9 on an MI50 (-1.84e-8 before), and in a host emulation of the kernel's arithmetic 3.2e-10 (-2.14e-8 before); two-float sums inside the folds as well came no nearer in emulation and cost about 5% at 16384 tokens on an MI50.
  A row's scores are partial dots over its lanes folded by a butterfly, its softmax runs online over the tiles from token 0 in order, so a row's result depends on its own history alone, whatever rows share its tile.
  `views` holds, a view each, its first row, rows, history, first block in `table` and first tile; `tiles` is their total.
- Causal attention of rows that attend one at a time (the Vulkan per-row design, attention_vec.comp), heads DIM wide, 128 or 256: a block a (row, head, split), streams of DIM / 8 lanes, each stream's softmax online and the streams merged in stream order.
  A row's splits are chunks of its own length; one split writes O and its twin (twin_at), several write partials for llmx_attention_vec_merge; a row whose end is 0 is the tile kernel's.
  SPARSE reads the row's `stride` selected ids in place of its positions, split in chunks of `chunk0` ids, a function of the stride alone; an id outside the causal prefix is skipped and a row of none gives zeros.
- The linear attention's causal conv of four taps, then SiLU (backend.hpp, causal_conv_silu), a thread a channel of a chunk of up to `chunk` rows of one view, as the CPU's multiply and fused multiply-adds in tap order, so a row is the same however its view is cut.
  tab holds the view count, five words a view (first row, rows, history length, source slot, destination slot), then two a chunk (view, first row); a view's first chunk reads its carried rows before it leaves its last three raw rows in slot dst.
- The gated delta rule (backend.hpp, gated_delta_rule) in the Vulkan shader's order (shaders/delta_rule.comp): a block a (view, V head j, 32 V columns), eight lanes a column holding 16 K rows each, q and k L2-normed and the gates made for each 16 tokens, every sum a lane's fused multiply-adds then lanes8.
  A sequence gives the same bits alone, batched or cut into passes; the decay is 0 below 2^-126. tab is causal_conv_silu's view table.
  The decode build stages 4 tokens a barrier and the prompt build 16; a token's decay is applied in the token before it or at its stage's start, the same products in the same order, so the two give the same bits.
  Both are bounded to 256 threads and two waves a SIMD, so a lane holds its 16 state rows in registers (127 VGPRs on gfx906); without a bound the compiler budgeted for 1024 threads, kept the rows in 304 bytes of scratch, and a one-row call took 74 us against 25 (docs/STATUS.md, ROCm decode steps 2 to 6).
- The Flash-Next stream ops (backend.hpp), each at its Vulkan kernel's op boundary and in its order (shaders/group_rms_norm.comp at fc6f53415, silu_scaled.comp, mix_streams.comp and inject_streams.comp at ca0f1f7df, signed_sqrt_gate.comp and dilated_conv_silu_add.comp at 7184ff13f), every value a function of its own row, the transcendental steps with expf.
  `llmx_signed_sqrt_gate` takes the sign 0 at a zero dot, or with its `kept` argument (`ZeroSign::kept`) the zero's own sign through `copysignf`.
  `group_rms_norm`, `silu_scaled` and `mix_streams`, and the gate ops `sigmoid_mul` and `gated_rms_norm`, write their output's twin beside it (twin_at) where the host asks for one: an output of whole blocks a row that a product reads next, at that product's class and map, so the product takes it without a twin launch; the map is read in place, since a pointer chosen at run time between it and null kept it in scratch.
- `hyper_mix` runs as persistent launches of up to 8 columns, `llmx_hc_mix` for one and `llmx_hc_mix8` for more in kernels/int16.gpu, for generated rows (decode and verify rows, every run of extent 1) over 8-bit activations on a 64-lane wave with Q8_0 down and up weights, an F32 inject product or none, dims of whole blocks and a low rank of at most 512, unless the shape is one the entry takes (below); any other call runs the default chain.
- A generated row's `inject_streams` on a stream dim of a multiple of 1280 and at most 8 streams is held as the backend's pending inject, which the next operation issues first; a `hyper_mix` at int8 on the same streams takes it instead, as one `llmx_hc_entry` launch of streams * dim / 1280 * low rank / 32 blocks, where that grid is resident, the low rank a multiple of 64 up to 512 and each block's mix rows fit 512 (docs/PRECISION.md, What each part computes in). The launches of `llmx_hc_entry` are counted with the other kernels'.
  Every other generated row of such a shape, verify rows and a row whose inject an operation issued first, takes `llmx_hc_entry8`, the same kernel over up to 8 rows already injected, which repeats each phase a row at a time on the down weights a block holds and its chunk's up weights, so each row has the one-row entry's bits and a row's bits never depend on the rows in its call (backend-rocm `hc_entry_rows`); both builds must be resident for the shape to take the entry, and a call of generated rows beside prompt runs mixes each stretch of one class alone (`mix_by_class`), so a decode row batched with another request's prompt keeps the entry's bits.
  The columns run one after another inside each phase, on the weights a wave has loaded, so a column keeps the one-column launch's bits and verify rows mix as decode rows, and the registers do not grow with the columns; its phases are the chain's kernels, each value with their chains and trees (group_rms_norm's sums, the half-block down rows a wave each, the F32 inject outputs a block each, silu_scaled, q8_0_half_pair's up rows two pairs a wave, mix_streams), split by four grid barriers on a counter in the launch's scratch that the last block out zeroes, so every launch starts from zero whatever its grid.
  The grid is ceil(low rank / 4) down blocks plus a block an inject output, and it launches only where hipModuleOccupancyMaxActiveBlocksPerMultiprocessor times the compute units holds it, read once a build; a grid past that runs the chain and says so once on stderr.
  Its grid barrier (`stores_sync`, `grid_arrive`, `grid_wait`, `acquire_sync`) keeps vector loads in flight across it on gfx9 before gfx940 alone, waiting on LDS and counting on the scalar path; gfx940 and later split L2 across dies and have no `buffer_wbinvl1_vol`, so they take `__syncthreads` and device-scope atomics as the other targets do.
- `delta_step` runs as the qkv and gate products, one group where every run is a generated row and the base's two products otherwise, since a prompt's tile splits by its call's outputs, and one launch of `llmx_delta_step` (kernels/f32.gpu) where `delta_holds` holds, and any other step runs the base's ops; the limits are named in `backend_core.hpp` (`kDeltaHead`, `kDeltaRows`, `kDeltaViews`, `kDeltaCounters`).
  The K and V head widths are multiples of 4 up to 128 (`kDeltaHead`), since a block holds a whole V head, 16 K rows in each of eight lanes and four adjacent V columns in each of 32 lane groups, and loads the state four columns a load.
  The V heads are any multiple of the K heads, so every tensor width's shard of Flash-Next (48/16, 24/8, 12/4, 6/2) and every layer split holds; a view has at most 8 rows (`kDeltaRows`), the rows its shared memory stages, and a launch at most 64 views (`kDeltaViews`) and 4096 (view, K head) counters (`kDeltaCounters`).
  A step whose views hold more than one row, a verify, takes the fused launch only where its views times V heads reach half the compute units: a block runs a view's rows in turn over a whole V head, while the base's delta rule spreads a head over Dv / 32 blocks.
  On one MI50 (60 units) a Qwen3.8-27B verify of four rows at int8 took 86.3 us fused against 79.4 us for the base on the 1x4 shard's 12 heads, 115.1 against 116.8 on 2x2's 24 and 179.1 against 189.9 on 1x1's 48; a device with more units sends more verify shapes to the base, and one-row views always fuse.
  The conv has four taps (`kConvTaps`), the alpha and beta matrices are of one type `delta_form` gives an order for, and the layer's slot and carried rows lie on four-float boundaries.
  `delta_form` is the base product's order: exact_sum for F32 rows at every dtype and for Q8_0 rows in the F32 class, and the row kernel's half-block order on the call's int8 twin for Q8_0 rows of an even block count in the int8 class, where every run is a generated row; the F16 class's quarter order and a prompt's tile are not held, and run the base's ops.
  A block a (view, V head) runs the alpha and beta products of its head in that order, llmx_causal_conv_silu's conv of its K head's q and k channels and of its V channels, the delta rule as llmx_gated_delta_rule_short takes it and llmx_gated_rms_norm's gate with the output's twin, the sigmoid or SiLU the step's `norm_gate` names (`sig`, as the norm kernel takes it), so every output, the alpha and beta slots and both state slots are the base's bits; the conv slot is not written, since nothing after the step reads it.
  The last block of a K head's V heads, counted on a (view, K head) counter it zeroes, writes that head's carried q and k rows once every block has read them, so no launch needs residency; the backend test `delta_step_bits` holds every output to the base's bits.
- `moe_router` at one row on a device of 64-lane waves, with a sqrt_softplus rule, an F32 or BF16 router and at most 512 experts (`kRouteStepExperts`, eight keys a lane), is one launch, `llmx_route_step_f32` or `_bf16`: a wave a router row as the one-row product (`exact_row`) takes it, then the last block out (a ticket on the step counter) picks on its first wave as `llmx_route_sqrt_softplus` does, so the scores, picks and weights keep the bits of the two calls; any other call, and every call on a device of 32-lane waves such as CUDA's, runs the base's two launches, as does a rule with a per-row bias (`RouteRule::bias_stride`), whose `llmx_route_sqrt_softplus` reads row r's bias r * bias_stride floats in.
  The step counter is one device word that `llmx_moe_step_route` and `llmx_route_step` share and each launch's last block resets, so it holds only while those launches sit on one in-order queue.
- `moe_step` runs as three launches where `fused_step` holds, and any other step runs the base's ops; the limits are the kernels' own, named in `backend_core.hpp` (`kStepExperts`, `kStepPicks`, `kStepIn`, `kStepFf`) and in the kernels beside them.
  The rows are generated rows, every run of extent 1, in the int8 class on a 64-lane wave with the dot module, while rows * k stays below the gate type's int8 grouped break-even (`TwinKernels::groups`, `group_from`) times the experts.
  From there the base's routed products group the entries and read each expert's gate and up rows once for all of them, which outweighs the fused step's fewer launches; at 10 of 512 experts and a break-even of 1.25 that is up to 63 rows.
  The rule reads the gate type's break-even alone, since the gate and up products are most of the step's weight reads: with a Q8_0 down of fewer than two spans of blocks a row, whose int8 half-block products group once the entries outnumber the experts, the base would group the down from 52 rows at 10 of 512 experts while the fused step still runs to 63 rows; Flash-Next's Q5_1 down shares the gate type's 1.25, so its measured gain is of the rule as written.
  The experts are a multiple of 64 up to 512, since `mf_route` holds n_expert / 64 keys a lane and is built for 1 to 8, and the picks 1 to 10, since the down stages k x ff twin values in shared memory.
  h is a multiple of 256 values up to 2560, since `gate_up` stages its twin in shared memory, and lies in device memory, since a twin of host memory is not kept and would take the slot the routed act's twin takes.
  The routed width ff is an even number of 32-value blocks up to 640, since the shared Q8_0 down takes the half-block order at any width while the base's row takes the quarter layout for an odd count.
  The router and the row gate of one output are F32, the routed gate and up Q4_K or Q5_K of the plain 32-lane row form, the down Q5_1 or Q8_0 of the plain form, the shared expert Q8_0 and as wide as a routed one, the scores softmax without bias or scale, the SiLU unclamped, and every output in device memory.
  `llmx_moe_step_route` (kernels/f32.gpu) takes the router's rows four a block with exact_wave's order, each row of h on its own in the one-row order, the row gates and the int8 twin of h, and its last block out routes each row by llmx_moe_route's rule on one wave of four, a pick the largest of 64-bit keys of probability bits over the complement of the id; the finished-block counter is zeroed by that block, so no launch needs residency.
