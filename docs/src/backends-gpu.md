# `src/backends/gpu/` - the GPU backends' shared core and kernels

The host core and kernels a GPU backend over a vendor runtime is built from ([ROCM](../ROCM.md)): one class template over the vendor's `Api`, its calls static functions, so no call is virtual, and kernel sources every vendor compiles; the ROCm backend ([backends-rocm](backends-rocm.md)) instantiates them over HIP, with the ops of the text architectures (`implements`) and the weight types of `kTypes`, on one device, over a layer split and in tensor groups; what remains of that plan is listed there (Scope on main, 2026-11-05).

- `gpu_backend.hpp`: what the core shows a vendor's public header, the forms of a tensor group's fast sum (`GpuSumForm`), which the tests name.
- `backend_core.hpp`: the backend (`GpuBackend<Api>`), with its buffers, graves and KV storage, each a template over `Api`: the vendor's types (stream, event, module, function, device) and its calls as static functions, which a vendor's translation unit supplies and instantiates once (`rocm/rocm_backend.cpp`, `HipApi`); a failed call reports the vendor's name and the call's (`Api::check`).
  - Execution: one non-blocking HIP stream a device, every op an asynchronous launch on it.
  - Records: a kernel launch (its function, grid and packed arguments, `Args`), a copy, a zero fill, or a handoff's wait for or write of a 64-bit word (`hold_wait`, `hold_write`) is held in the backend's record and issued in order at a flush, which first makes the device the thread's current one, since HIP finds a module's function through it and another backend's call may have changed it. A flush comes every `dispatch_chunk` held operations (the profile's), after the first 8 where the submission opened with nothing running on the device, at every submission and before every host wait that could cover held work (a dropped view of registered host memory, the destructor), and a tensor group flushes all its members before a sum and again once the sum's launches are held, so no member's sum kernel waits on a peer whose work the host still holds and the conservative path's events follow what they cover. A ring wrap submits only where the slot it takes next was read since the last submission, which no stage reaches, so a wrap is not a flush point and a stage's chunks follow its operations alone. A failure HIP reports as an operation is issued throws naming it, and the operations held after it are dropped.
  - Tickets: `submit()` records an event from a ring of 1024 and returns its ticket from the shared `TicketLedger` ([backend](backends-backend.md)), and a slot is reused only once its earlier ticket has retired. `wait` synchronises on the ticket's event and `done` queries it, but reads an event some thread is synchronising on as not done without asking HIP, which holds such a query until the work ends: the recording thread asks `done` as each submission opens, and a pipelined prefill's completion lane synchronises on the last stage's tickets (docs/STATUS.md, A ROCm ticket some thread synchronises on reads as not done).
    The ticket events are timing events, and a second ring of start events, one recorded before a submission's first operation that is not a wait on another device's word, gives `busy_ms` its time from there to the ticket event without waiting, -1 once a slot is reused.
  - Products into host memory (the logits): a product whose output is pinned host memory is formed in device memory and copied over whole, since the row kernel's one float a row over PCIe took the 0.6B's head 3.3 ms of a token.
  - Memory: `alloc` is device memory zero-filled on the stream, or pinned host memory the device reads in place (`Memory::host_visible`); `wrap_host` registers the caller's host memory with HIP, which registers an address once for every device, so the views of one memory on several devices (a head's tensor group's logits rows, the loader's read ring) count against one registration, and the last view dropped waits for its stream's copies and unregisters it at once rather than through the graves: HIP keys a registration by address, and one left behind after the caller freed its memory was taken for the next memory mapped there, whose copies faulted the device; HIP takes a second registration of a span and drops it at one unregister, so the count is the backend's, and a second span at a registered address, or one HIP refuses, gives no view, so the caller writes through staging; `copy` between two host memories, as a tensor group's head copies its member logits into the rows its members wrap, is `llmx_copy` on the stream through the device addresses HIP gives (`hipHostGetDevicePointer`), since HIP makes such a copy on the host once the stream has drained, which held the host about 7 ms a token on 2x2 (docs/STATUS.md, ROCm decode loop); `write` and `read` go through a pinned staging ring, and host values a kernel reads (positions, ids, block tables) through an argument ring, each slot reused once the ticket that last read it retires. The values every layer of a pass reads alike, attention's block table, firsts and ends, the KV write's blocks and slots and the positions, go through `pass_arg`: the first layer to name a set copies it from the argument ring into a ring of device memory on the stream ahead of its launch, and a later layer whose set has the same bytes reads that copy, so the kernels read device memory and not pinned host memory over PCIe; the host compares and never waits for the copy, and a device slot is taken again only once the last launch that read it retires. A dropped buffer's memory waits in the backend's graves until the work recorded before the drop is done, since `hipFree` unmaps it at once even while a queued launch or copy names it: a model buffer dropped mid-prefill faulted a 16K prompt. The graves are freed by a thread the backend owns, never by a thread that records or waits: once a grave's covering ticket is recorded the thread synchronises the stream and frees it, because `hipFree` and `hipHostFree` hold their caller until all the work queued on the device has run, which on a pipelined prefill's recording thread stopped its stage feeding the next, while a stream synchronise on another thread holds neither the launches nor the event queries of the thread that records (docs/STATUS.md, ROCm frees beside the devices); an allocation HIP refuses first waits for the graves under recorded tickets to be freed, which waits for the whole stream since the thread synchronises it, and is tried once more; it records nothing, so a drop since the last ticket is not counted. `memory_available` frees the recorded graves the same way before it reads, and `sync` records a ticket for drops since the last one, so a reading after `sync` counts every dropped buffer as free, as the fit needs.
  - Errors: a call refused as it is enqueued throws at once; a failure the device reports at an event is kept as the first cause, which `raise(t)` before results are read in place, `read` and the next launch or submission throw.
  - KV: blocks of 64 tokens through the shared `BlockKVStorage`, F32 or F16 sides, with a layer's auxiliary F32 rows and pooled-row room in their own plane of the same blocks (`kv_alloc`'s widths and pools), which `kv_write` fills token-major through the storage's copies (`write_aux`), an old buffer a growth copied from dropped into the graves like any other.
  - Weight types: one descriptor row a type (`kTypes`), naming the F32 class's exact product, the embedding and the type's twin kernels (`TwinKernels`: its row builds by form and columns, the output rows a wave of each takes, its four-row builds and its tiles, tall or not), which every caller reads, so no caller switches on a type; `supports_type` is that table. F32, Q8_0, Q4_K, Q5_K, Q6_K, Q5_0, Q5_1, BF16 and IQ4_NL are in it, and Q8_0, Q4_K, Q5_K, Q6_K, Q5_0, Q5_1 and IQ4_NL have twins, IQ4_NL's grid values as signed bytes, sign-extended in the 16-bit words: BF16 takes its exact product in every class, wider than asked, as Vulkan takes its F32 rows, which `dtype_path` names from the table and the product records as the F32 path. `rocm_take_launches` gives the kernels launched since its last reading by name, the witness of which row build, tile or exact kernel ran. `rocm_profile` gives the profile the backend shapes its kernels by, which `kv-selection` reads and changes to run each selection form at one size.
  - Ops: `matmul`, `matmul_add`, `matmul_group` (one twin for the group's projections, kept for the next product of the same activations in one of two twin slots, the newer first, a new twin taking the slot not holding the newer kept one and a twin a product reads becoming the newer, so the routed act's twin leaves the mixed streams' for the shared expert; a launch writing only an exact product's, a router's, a grouping's or a producer's outputs, or a copy, keeps both unless it writes a kept twin's input, `launch_writing` and `forget_written`, the one owner of forgetting them, while any other launch, a write or an allocation drops both; `group_rms_norm` writes four values and their twin a thread, in aligned 8-lane groups of a wave, where its operands lie on 16 bytes, and one a thread otherwise, the same bits either way) and through them `matmul_logits`, on the table's types: in the F32 class every type decoded exactly into F32 sums, in the F16 class Q8_0, the K-quants, Q5_0, Q5_1 and IQ4_NL on the block-int16 twin and in the int8 class on the block-int8 twin (`native_dtypes` {f16, f32, int8}, docs/PRECISION.md, section 5); `embed` of a table of any of them, at 64-bit offsets, and `embed_ids` through the same gather a type (`llmx_gather`, `llmx_gather_<type>`, which take the table's row count and write a +0 row for an id at or past it) with the ids read on the device, `argmax_rows` (`llmx_argmax_slices`, a block a slice of the profile's `argmax_slice` logits, then `llmx_argmax_merge` taking a row's slices in order on one lane, each step keeping the larger value, the lower id of equal values and a NaN or +inf flag, and refusing a row of no ids as Vulkan does), `gather_rows`, `rms_norm_rows`, `norm_rope_partial` over several rope streams, `gated_rms_norm`, `sigmoid_mul`, `causal_conv_silu`, `gated_delta_rule` (a block a view, V head and 32 V columns, in the Vulkan shader's order, so a sequence gives the same bits however its views are cut; the build staging 4 tokens where every view of the call holds at most 8 rows, as Vulkan chooses its short build, else the one staging 16), `norm_rope_kv`, `silu_mul`, `add`, `copy`, `kv_write`, `attention`, the Flash-Next stream and conv ops (`group_rms_norm`, `silu_scaled`, `mix_streams`, `inject_streams`, `signed_sqrt_gate`, `dilated_conv_silu_add`, in `kernels/f32.gpu` at their Vulkan kernels' op boundaries and orders, F32 outputs, each row from that row alone and the conv's view in chunks of at least its history, so only a view's first chunk reads and leaves its carried raw rows), and the routed experts (`Op::routed_experts`): `route_experts` (a row a block of 64, its reductions the 64-pair tree, in the Vulkan kernel's order), `matmul_experts` and `matmul_experts_add`, each entry through its type's one-column body over its expert's rows (`llmx_routed_<type>` in the F32 class, the twin types' `routed16`, `routed8` and `routed_half8` builds in the others, `routed_half8s1` on rows under two spans of blocks as the dense one-column build), so an entry gives the bits of its expert's one-column product; in the twin classes a call from its build's break-even (`TwinKernels::group_from`) groups them, but for a half-block call of at most one entry an expert on rows under two spans of blocks or from four, which takes the one-column build an entry and no grouping launch, since that build fills its one or four steps there and the grouped build's two steps are faster between, by expert (`llmx_moe_group`, the Vulkan grouping) and runs each group of up to 2, 4 or 8 entries, the narrowest holding their average, through the row build of that many columns (`routed16_g<C>`, `routed8_g<C>`, `routed_half8_g<C>`), a column an entry, whose twin column and outputs the build reads from the group (`EntryCols`), so each entry keeps its one-column bits and an expert's rows are read once a group; a prompt's rows from its build's tile extent for the call's role, gate and up or the down (`TwinKernels::tile_from`), take the routed tile instead (`routed_tile16`, `routed_tile8`): the grouping in groups of up to 64 entries, each group a block row of the prompt tile's 64 by 64 design over its expert's rows, or of its narrow build of 16 rows (`routed_narrow16`, `routed_narrow8`) where the group's entries fit them, both launched and each group running in one, never split, each entry's blocks summed in order in both, so an entry's sums are its own, the same in either build and within the tile's bound of its one-column product; and the down slots joined in slot order by `llmx_moe_combine`; `moe_step` is the base's sequence of them, or three fused launches where `fused_step` holds (Kernel notes, below); `delta_step` is the base's chain of the linear-attention ops, or the qkv and gate products and one fused launch where `delta_holds` holds (Kernel notes, below); and the indexer, `pool_kv` and `select_kv`, both pooling through one kernel (`llmx_kv_index_pool`), `select_kv` then scoring at most 16 rows at once (`llmx_kv_index_scores`) and selecting in one of two forms by the view's complete groups, the one-block selection (`llmx_kv_index_select`) below the profile's `select_wide_from` and from it the five-launch wide form over slices of 1024 groups (`llmx_kv_index_select_wide`), both by raw score bits with ties to the earlier group, so they give the same ids; and `sparse_attention`, each row over its selected ids, through the per-row attention body's sparse build for heads 128 and 256 wide (`llmx_sparse_attention_vec`, `llmx_sparse_attention_vec256`, the dense body's template with its head width a parameter) split in chunks of 256 ids and merged in split order (`llmx_sparse_attention_vec_merge`, `_merge256`), and through the chunk body's sparse build for other widths (`llmx_sparse_attention_chunk`, `llmx_sparse_attention_merge`), chunked by the id stride, so a row's splits follow the stride alone; an id outside the row's causal prefix is skipped and a row of none gives zeros; and DeepSeek-V4.1's ops (docs/DEEPSEEK4.md, section 4.2), a kernel each, `topk_rows` and `candidate_blocks` one (`llmx_topk_rows`, a block a row, the picks' least key found four bits a round from the top by a radix select over a histogram a wave in shared memory, the row read four keys a lane, and each pick's place ranked by wave ballots), `route_experts` under the sqrt_softplus rule its own, a wave a row with exact argmax picks by shuffles and the sum in pick order on one lane (`llmx_route_sqrt_softplus`), `hc_collapse_norm` writing its output's twin beside it where the row is whole blocks, as `rms_norm_rows` does, `norm_rope_partial`'s other forms their own (`llmx_norm_rope_form`) and `silu_mul`'s clamp an argument of its kernels, the pooled-row ops reading the auxiliary plane through a table of each row's block ids and position (`pooled_table`), and `moe_step` the base's sequence for either rule and a clamp. Every other weight type and named op is refused at load (`supports_type`, `implements`), `mixed_experts` among them, and `join` makes a tensor group's collective (`collective_core.hpp`, below).
  - Memory: `memory_available` is HIP's free device memory, and the fit leaves no share of it: `resident_bytes` and `scratch_bytes` count each buffer at the pages hipMalloc takes, its units read at construction from the free memory 64 4-byte and four 1 MiB + 4 byte allocations take (`probe_memory`, `allocation_unit`, 2 MiB where a reading fits no power of two). The small unit is the sub-allocator's average over the 64, not a page (32 KiB on an MI50, whose small buffers share 2 MiB pages), which prices a buffer below 1 MiB as the runtime places many of them. Scratch: every scratch buffer's size for a call comes from one function its grow site and `scratch_sizes` share (attention and sparse parts, the sink's rows, the routed slots and groups, the fused step's twin, the tile split's partials over `split_partials_most`, the indexer's scores and state, argmax slices, the hyper-connection mix, both twin slots at the 16-bit class with each map region's padding, the host-bound head's staging), and `reserve_scratch` makes each at the widest call the widths allow. A call with any row on the per-row attention kernel prices all its rows at that kernel's split count, which is the kernel's layout, not a margin. `memory_kept(free)` ignores the fit's reading and is the runtime's private scratch for kernels that spill (the largest `HIP_FUNC_ATTRIBUTE_LOCAL_SIZE_BYTES` of any kernel times the lanes a compute unit holds and its compute units, none where no kernel spills) and a group's signal block; without the old 256 MiB and twentieth a server fitted to the whole card relies on these being exact, which the `backend-rocm-scratch` test holds.
  - Batch invariance: every kernel computes a row from that row alone in a fixed order. `row_class` makes a generated token one class; a prompt's rows are classed by the product tile's column tiles at their extent (`split_tiles_of`, up to 512 rows), which choose its inner split, by how many routed builds' tile extents (`TwinKernels::tile_from`) it reaches, which choose the routed tile, and by whether the extent reaches the profile's `attention_tile_rows`, which chooses the attention tile, so a choice follows the rows' prompt and never the rows a call holds.
- `collective_core.hpp`: a tensor group's collective (`GpuCollective`, docs/ROCM.md, step 4), which `backend_core.hpp` includes after the class; `join` takes two to sixteen devices of one backend and kind, each once, led by the backend it is called on.
  - Fast path, the one-shot: each member's `llmx_group_sum` kernel (`kernels/f32.gpu`), on that member's own stream behind the work that wrote its partial rows, writes them into its slot in every peer's area, uncached memory (`Api::malloc_uncached`, `hipExtMallocWithFlags` on ROCm) that a peer's stores reach without the fine-grain setting, and takes each peer's rows from its own slots as they land, with no flag and no meeting: a slot holds the signalling NaN 0x7f800001 (`kGroupArmed`) until its value arrives, a sender's value of those bits goes as its quiet twin 0x7fc00001, and a receiver spins on each unit of four floats (a float at a time in a tail) until none holds the armed bits, adds the members' rows in member order, its own from its partial rows unsanitized and the others' from its slots, as `sum_rows.comp` adds them (t = p0, t += p1, ..., then residual += t, or residual = t in place), and arms the slots it read again. Every value meets at least one add at a width of two or more, and an add quiets a signalling NaN, so the twin is invisible in the bytes, which `join`'s probe checks on every member; the bytes are the Vulkan collective's. The slots come in two parity halves, armed by `llmx_group_arm` at join: the host flips the half at each one-shot and passes it in the flags (4), the same for every member and block, so a member writes a half only once every peer has finished the sum before last, which it did before sending the last one's values, and two sums may be in flight on one collective. Up to 16 blocks, each member's `GroupPeers` written once at join into its own device memory and passed by address, so the launch's arguments do not grow with the width (`kGroupMembers`, the kernel's `GroupSignal` and `GroupPeers` sized by `backend::kMaxTensorWidth` and pinned by `static_assert`s on both sides). QDEV7's breakdown measured a 20 KB sum at 8.5 against 17.4 to 18.1 us over four MI50s of one root complex with the flag, fence and two meetings it replaced (docs/STATUS.md).
  - Two other forms move a large sum's rows (TENSOR-SPLIT section 4.3), each adding every element as the one-shot does, `((p0 + p1) + ...) + p(W-1)` and then the residual, so every form gives the one-shot's bytes at any size and width for every value but a NaN made of two NaN inputs, whose payload may follow either input.
    Two shots: the units are cut into a share a member, whole units of four floats; every member pushes share k of its rows into member k's staging and meets, member k adds the share in member order into its own output and into every peer's own slot and meets again, and every member then adds the shares it gathered; 2 (W - 1) / W of the rows leave a card in place of W - 1, up to 32 blocks.
    The chain: member m adds its partial rows to the running sum member m - 1 passed into m's own slot and passes the result to m + 1, chunk by chunk (4096 units), and the last member's total flows back down through each member's slot m + 1, so the rows cross only between neighbours in member order.
    The wrap, the chain's kernel with flag 8, adds the same way and sends the total on around, W - 1 to 0 to 1 and on to W - 2 through each member's slot m - 1, so each card sends to one peer; every chunk still flows 0 to W - 1 unrotated and the total is formed once at member W - 1, so its bytes are the chain's, and at width 2 the two are the same route.
    In both, blocks [0, F) carry the sums ahead and [F, 2F) the totals back, F up to 16, chain block b takes chunks b, b + F, ..., and each chunk is told by a running count in the receiver's signal block (`ahead`, `back`) that every member's `passed` counts keep equal.
    Every form ends at a meeting, so a sum in any form may follow one in any other on the same collective; each takes the parity half the next one-shot takes, which every peer finished reading at the one-shot before the last, and a reader arms the one-shot's slots it read again before the last meeting, so the one-shot still finds them armed. Their meetings' epochs live in the signal block, one a block, and skip 0 on the 32-bit wrap, since fresh slots hold 0.
  - The form: a sum of n floats takes the form that won at the largest timed size not above n, the one-shot below them all. `join` times the forms on the group's own cards at its first collective of a size past what was timed for the group, its members idle: each form's least time over three sums in place after a first (`timed`), at the reserved rows and halvings of them, whole rows down to one so a generated row is a timed size, to where the one-shot wins or to 4096 floats, kept with the probe's answer by the first member and printed on stderr once a group and size (`rocm: tensor group of devices 0, 1, 2, 3 timed its sums in place, ms one-shot, two shots, chain, wrap: ...`), since which form wins follows the cards' places on the PCIe tree, which no device number gives; a launch that fails while timing leaves the group conservative, as a failed probe sum does.
  - The member order (`member_order`, docs/TENSOR-SPLIT.md, section 4.1): asked once a listing before any weight loads, it probes the group as listed, then costs an order as its fastest form at the pass's rows on a collective of its own, by swap descent from the listed order, a swap taken only where it beats the order kept by `kOrderMargin` (4%), and prints `rocm: tensor group of devices 0, 1, 2, 3 takes member order 3, 0, 1, 2, ...` with the orders timed. The winner's forms are timed into the path of the group as ordered, kept by its first member, so its `join` times nothing up to that size; every collective it timed is freed before the fit reads free memory, and the order is kept for the listing, so a second model on the same backends takes the same order. A group on peer pulls, of one member or below 4096 floats keeps the listed order. `rocm_collective` (`rocm_backend.hpp`) makes a collective whose fast sums all take one form, its members possibly backends of one device, for the tests; there is no flag.
  - Failure: a member waits for a late peer as long as it takes, since the host issues every member's sum together and each depends only on work issued before it, so an alive peer always comes. Its waits give up only when a peer set the area's abort word, when the host set the collective's cancel word, which it does where a member's launch of the sum throws, read once a millisecond of the device's wall clock (`hipDeviceAttributeWallClockRate`), or, in `join`'s probe alone, after one second of that clock, where peer writes that never become visible are what the probe looks for. The kernel then leaves NaN where its sum would be, leaving the slots it did not read unarmed, which no later fast sum reads, sets the abort word in every member's area, the collective's status word and its backend's fault word, both in pinned host memory. The fault word throws once at that backend's next check (`raise`, a launch or a submission), and the collective, which reads its status words in `wait` and before each sum, takes the conservative path for every later sum. A sum checks every member's failures before it launches on any, so no member waits for a peer whose launch threw. A live peer always arrives, since the host enqueues every member's sum in one order with no cycle, and a hung device hangs the sum, as the pull path and Vulkan's collective already do.
  - Conservative path: each member records an event once its partial rows are written, pulls every peer's rows into its staging behind that peer's event, records a second event, and sums with the same kernel, in the same order, once every peer's second event says it has read its rows. It is taken from the start where `join`'s probe fails: a directed pair that cannot reach the other's memory, peer access refused, a member whose add tells a value from the twin the one-shot sends for the armed bits (`GpuCollective::add_check`: `llmx_group_add_check` adds 13 patterns, the armed bits, their twin, both signs of signalling and quiet NaNs with payloads, both infinities, both zeros, a denormal and a normal, as a + b, (a + b) + c and c + (a + b) raw and sanitized, read from memory the host wrote), or one fast sum of known rows that gives other values or gives up. It pulls into the first parity half.
  - The probe runs once per group of device indices, its answer kept by the first member, and its decision goes to stderr once (`rocm: tensor group of devices 0, 1 sums by peer writes`, or by peer pulls with the reason). `collective_bytes_per_row` counts a member's partial rows and two parity halves of a staging slot for each member, the fast path's, more than the conservative path's one half, and `memory_kept` the 8 KiB signal block before them.
- `collective_core.hpp` also holds the handoffs (`GpuHandoff`, `handoff(readers)`), a crossing's order on the devices over the sender's pinned host buffer ([MULTI-DEVICE](../MULTI-DEVICE.md), Execution structure), kept by 64-bit counters in coherent host memory, the sends and each reader's takes, which stream memory operations write and wait for (`hipStreamWriteValue64`, `hipStreamWaitValue64`): `sent` writes the next send count on the sender's stream, `take` makes a reader's stream wait for it once per send and copies on that stream, `taken` writes the reader's next take count, and `begin` makes the sender's stream wait for every reader's count to reach its takes so far.
  These are held with the backend's other records, so they keep the stream's order, and `sent` and `taken` flush at once, so no host wait on a ticket can stand behind a device waiting for a mark still held.
  Events would not do: a HIP event waited for on another device's stream held the calling thread until the event completed, 10 ms of a 10 ms sender in `backend-rocm handoffs`, so the host would wait as before.
  A reader's first copy out of a sender's host memory holds the caller about 6 ms on two MI50s, once a device pair: a new buffer of a warm pair took 0.012 ms the first time (`backend-rocm handoffs`, six MI50s), so no priming is needed, and the copies after it are queued in microseconds.
  Every ROCm reader is served, a reader of another backend is not, and a handoff serving none is null; the reader copies from host memory, so no peer access is needed. A take count advances only once the flush that issues its write returns, as the send count does, and a reader's wait counts as made only once the flush that issues it returns, so a flush that throws drops a write no stream waits for and a wait the next take makes again; the destructor drains every side's stream before it frees the counters.
- `kernels/port.h`: the one kernel file naming a vendor's intrinsics: each construct the kernels use (the wave width the code is compiled for, `GPU_WAVE`, lane exchanges, byte align and permute, the integer dots, first-lane broadcast, ballot, scoped atomics and fences, sleep, wall clock, scheduling barrier, address spaces and word vectors) as a small function named by what it does, which under HIP is exactly the builtin it wraps, so the code objects are unchanged; each permute, swizzle and DPP wrapper states the selector values the kernels pass.
- `kernels/quant.h`: the one reader of block layouts on the GPU backends, the device counterpart of the Vulkan block decoders: for each type its values and bytes a block from `src/quant/types.hpp` and `value`, one value decoded with the CPU dequantizer's bits; `f32.gpu` and `int16.gpu` include it.
- `kernels/int16.gpu`: the quantized products of the F16 and int8 classes (docs/PRECISION.md, rule 4 and section 5), reading the twin `kernels/f32.gpu` writes: the Q8_0 row kernel for generated rows, which in the int8 class on rows of an even block count takes the Vulkan decode kernel's half-block order (`matmul_vec_q8_one.glsl`, `HALF`), two lanes a block, the even lane the scale and 16 weights and the odd lane the other 16, each as aligned words realigned in registers without a branch, the scale handed from the even lane to the odd, and four 8-bit dots against one 16-byte read of the twin, on the dot module where there is one, and otherwise the quarter layout, four lanes a block, a wave taking two or four output rows by the call's rows (`row_build`): the builds of two to eight columns take four once the call launches the profile's `row_four_waves_per_cu` waves a compute unit at four rows a wave and two below it, the F16 class's one- and sixteen-column builds two, the int8 quarter layout's one-column build two and its sixteen-column build four, the half-block order's builds of 9 to 16 columns two, one build a width, the host taking the narrowest that holds the call (`kHalfWide`), since at four rows a wave they held more than 128 VGPRs and ran one wave a SIMD on an MI50, a 256-VGPR register file, each twin load serving every row of the wave and each row keeping its lanes and order; the builds of four columns and more load the twin a group of columns at a time ahead of the group's products, a column past the call reading column 0 and storing nothing (in the half-block order skipped up to 8 columns and read as the call's last column in a wider build, so no column branch splits its loads), and a build wider than its group addresses every column from one 32-bit lane offset rather than a pointer a column; and the prompt tile.
  The prompt tile takes the Vulkan tile's design (`matmul_tile_q.comp`): 256 threads, 64 outputs by 64 rows, each thread 4 adjacent outputs by 4 adjacent rows, the blocks of a step (four for block-int8, two for block-int16) staged k-major in shared memory with the weights widened to the twin's integer type, four threads a twin row and 256 / outputs threads a weight row (four, or two on the tall build). A step's weights load as aligned 4-byte words realigned in registers, since a Q8_0 block is 2-byte aligned: a thread's share of a block, a quarter or a half, as one vector load of its words and one word more, the word before or after by its alignment, the scale taken from them. Every load of a step goes out before any is waited for, out-of-range ones at a valid address with their zero chosen at the store, each at a 32-bit byte offset off the tile's first output or row held in scalar registers (`at`), with no 64-bit address arithmetic, and the next step loads while the current one computes. Buffers are allocated in whole words, since the last word of a final block may run past it. A thread reads its outputs' and rows' word as two 16-byte reads and feeds 16 integer sums; each output sums its blocks in order, acc = fma(dw * dx, isum, acc). A tall build of 128 outputs, each thread 8 outputs by 4 rows, two blocks a step in both classes, the block-int16 one loading its step after the barrier rather than while the previous step computes, sums each output in the same order and keeps the 64-output build's inner split, so a call takes it by the device profile's `tile_rows_for` without a change of bits; the MI50's HIP row takes it on rows from 4096 wide at 6 workgroups a compute unit (docs/STATUS.md, ROCm tall tile).

a type's lane (`KRaw`'s `Lane`) loads its share of a block, Q4_K and Q5_K eight lanes a block of two 16-value runs each, Q6_K sixteen lanes of 16 values, Q5_0 and Q5_1 one lane a block of 32 values, and the quarter form (`QuarterLane`) four lanes a block of 8 values through the type's own raw load and decode, the tile's arithmetic; a Q5_0 or Q5_1 row takes the quarter form where its lane units fill the cluster's steps fuller than one lane a block, one lane on a tie (`row_form`; on a 64-lane wave 640 and 1024 wide one lane, 2560 and 1056 the quarter form); each lane adds its runs' terms in block order and the cluster folds them by one xor tree (`store_cluster_sums`), transposed where the cluster has a lane for every sum; the cluster and the form follow the row's width and type alone, so a row and every routed or grouped entry of it give the same bits; Neither has a four-row or tall build yet.
  The tile reads its twin block-major: the backend lays the twin out from the call's runs (`TwinMap`, one place, which the twin's producers and the products share), a run of generated rows row after row as the row kernels read it, a prompt's rows with block k of every row of its region together and the rows padded to an odd multiple of 4, so a stage's rows are one coalesced read and block k + 1 starts on other memory channels than block k; neighbouring runs of one kernel share a region, and neighbouring runs of generated rows, or of prompts of one inner split, share their launches, so a decode pass of four sequences reads each weight once; a call of more regions than the map's eight lays every row row after row, which the tile reads through its row and block strides as well. It moves where a value lies, never a value, so the bits are the same either way (docs/STATUS.md, ROCm block-major twin). Each twin producer has a map-free build, which a call whose twin lies row after row takes, and a build reading the map (`_major`), so decode runs no code of the map.

- Contraction: every kernel compiles with `-ffp-contract=off` (`LLMX_HIP_FLAGS` in `CMakeLists.txt`), since whether HIP fuses `a * b + c` depends on the product's other uses after inlining, which differ between the builds of one body; the order of each kernel (op boundaries, tiles, splits and merges) follows the Vulkan design, and every multiply-add accumulation is written as `fmaf`, attention's online softmax `l`, its score dots and the merges' `L` and `A` among them, so the bits hold between ROCm's own builds and classes; across backends ROCm is held to the CPU's bound and to HF, not to Vulkan's bits.

## Kernel notes

What the kernels' comments leave out, file by file and in file order: their layouts, their orders of work and why they take them.

`kernels/f32.gpu`:

- The dense F32 kernels of the ROCm backend (docs/ROCM.md, Delivery checkpoints, step 2) and the activation twins the quantized products read: every sum is F32 in a fixed order that depends on the row alone, never on how many rows a call holds.
  A block reduction folds lane partials in one tree whatever the wave width, so a row gives the same bits in any call.
- A block a row of n <= K * kThreads values: dst = RMSNorm(src) against w, with its twin at L levels beside it when L is not 0, the rows then dense and n a multiple of 32.
  Each of the block's kNormThreads threads loads its values and their weights at once, element t + kNormThreads j; the sum is rms_norm_row's, thread t < kThreads chaining elements t + kThreads k and the chains folded by block_sum's tree, so both give the same bits.
- Member `rank`'s part of a group sum of n floats: out = the members' rows added in member order (flag 1), or out += them.
  Fast (flag 2), the one-shot: write its own rows, sanitized (`group_sane`), into its slot of every peer's parity half (flag 4), then take each peer's unit from its own slots once no float of it holds the armed bits, add in member order and arm the unit again (`group_take`); otherwise the host has pulled the peers' rows into its staging.
  A thread's wait gives up as `group_stop` says, looked at every 64 spins (`kGroupSpinChecks`), or once another thread of its block has; a sum that gave up leaves NaN in out.
  `llmx_group_two_shots` and `llmx_group_chain` take the same arguments for two shots and the chain and wrap (`group_two_shots`, `group_chain`, flag 8 the wrap), kernels of their own so the one-shot keeps its registers and a group of 16 ranks stays resident on one device, each ending at a meeting after arming again the one-shot slots it read; a chain block whose wait failed leaves NaN in every chunk it writes into out.
  `llmx_group_arm` arms a member's staging at join, and `llmx_group_add_check` is the probe's check of the add's NaN rule.
- A block a (row, head, chunk) of the split attention: 64 positions a tile, four threads a position's dot and one thread a dimension's accumulator, an online softmax over the chunk's tiles in order.
  The chunk's maximum, sum and accumulators go to `part` for llmx_attention_merge.
  SPARSE reads the row's `stride` selected ids in place of its positions, chunked by the stride alone, an id outside the row's causal prefix (`ends`) skipped.
- Causal attention of a prompt's rows (the Vulkan tile's design, attention_tile.comp): a block a tile of 32 query rows of one view and one head, eight lanes a row each holding 16 dimensions of the scaled query, K and V through shared memory 16 tokens at a time.
  A row's scores are partial dots over its lanes folded by a butterfly, its softmax runs online over the tiles from token 0 in order, so a row's result depends on its own history alone, whatever rows share its tile; heads 128 wide.
  `views` holds, a view each, its first row, rows, history, first block in `table` and first tile; `tiles` is their total.
- Causal attention of rows that attend one at a time (the Vulkan per-row design, attention_vec.comp), heads DIM wide, 128 or 256: a block a (row, head, split), streams of DIM / 8 lanes, each stream's softmax online and the streams merged in stream order.
  A row's splits are chunks of its own length; one split writes O and its twin (twin_at), several write partials for llmx_attention_vec_merge; a row whose end is 0 is the tile kernel's.
  SPARSE reads the row's `stride` selected ids in place of its positions, split in chunks of `chunk0` ids, a function of the stride alone; an id outside the causal prefix is skipped and a row of none gives zeros.
- The linear attention's causal conv of four taps, then SiLU (backend.hpp, causal_conv_silu), a thread a channel of a chunk of up to `chunk` rows of one view, as the CPU's multiply and fused multiply-adds in tap order, so a row is the same however its view is cut.
  tab holds the view count, five words a view (first row, rows, history length, source slot, destination slot), then two a chunk (view, first row); a view's first chunk reads its carried rows before it leaves its last three raw rows in slot dst.
- The gated delta rule (backend.hpp, gated_delta_rule) in the Vulkan shader's order (shaders/delta_rule.comp): a block a (view, V head j, 32 V columns), eight lanes a column holding 16 K rows each, q and k L2-normed and the gates made for each 16 tokens, every sum a lane's fused multiply-adds then lanes8.
  A sequence gives the same bits alone, batched or cut into passes; the decay is 0 below 2^-126. tab is causal_conv_silu's view table.
  The decode build stages 4 tokens a barrier and the prompt build 16; a token's decay is applied in the token before it or at its stage's start, the same products in the same order, so the two give the same bits.
  Both are bounded to 256 threads and two waves a SIMD, so a lane holds its 16 state rows in registers (127 VGPRs on gfx906); without a bound the compiler budgeted for 1024 threads, kept the rows in 304 bytes of scratch, and a one-row call took 74 us against 25 (docs/STATUS.md, ROCm decode steps 2 to 6).
- The Flash-Next stream ops (backend.hpp), each at its Vulkan kernel's op boundary and in its order (shaders/group_rms_norm.comp at fc6f53415, silu_scaled.comp, mix_streams.comp and inject_streams.comp at ca0f1f7df, signed_sqrt_gate.comp and dilated_conv_silu_add.comp at 7184ff13f), every value a function of its own row, the transcendental steps with expf.
  `llmx_signed_sqrt_gate` takes the sign 0 at a zero dot, or with its `kept` argument (`ZeroSign::kept`) the zero's own sign through `copysignf`.
