# `src/backends/rocm/` - the ROCm backend

The ROCm backend over HIP ([ROCM](../ROCM.md)), built only with `LLMX_HAS_BACKEND_ROCM` on Linux: the ops of the text architectures (`implements`) and the weight types of `kTypes`, on one device, over a layer split and in tensor groups; what remains of that plan is listed there (Scope on main, 2026-11-05).

- `rocm_runtime.hpp`: the HIP runtime opened at run time with `dlopen`, its calls in one table (`hip()`) loaded by their exported names, so a build with the backend still runs where no ROCm is installed; a test substitutes a call in it to inject a failure. A missing library, call or device throws `RocmUnavailable`, which the caller reports as a missing device. `hip_check` turns a failed call into a runtime error naming the call and the runtime's reason.
- `rocm_device.hpp`: a device as HIP reports it (`rocm_device(index)`): its wave width, compute units, name and runtime version in `DeviceCaps` ([device_profile](backends-device_profile.md)), and beside them its ISA, memory, PCI address and root complex (`pci_root_of`), and its `DeviceProfile`, which the backend takes once from `profile_for` after it knows the integer dot and reads wherever a kernel's shape follows the profile.
- `rocm_backend.hpp`: `make_rocm_backend(index)`, the one entry the device factory ([devices](backends-devices.md)) reaches for `--device rocm:N`.
- `rocm_backend.cpp`: the backend, a translation unit of its own as the Vulkan backend's is.
  - Execution: one non-blocking HIP stream a device, every op an asynchronous launch on it, each launch first making its device the thread's current one, since HIP finds a module's function through it and another backend's call may have changed it; `submit()` records an event from a ring of 1024 and returns its ticket from the shared `TicketLedger` ([backend](backends-backend.md)), and a slot is reused only once its earlier ticket has retired. `wait` synchronises on the ticket's event and `done` queries it.
  - Products into host memory (the logits): a product whose output is pinned host memory is formed in device memory and copied over whole, since the row kernel's one float a row over PCIe took the 0.6B's head 3.3 ms of a token.
  - Memory: `alloc` is device memory zero-filled on the stream, or pinned host memory the device reads in place (`Memory::host_visible`); `wrap_host` registers the caller's host memory with HIP, which registers an address once for every device, so the views of one memory on several devices (a head's tensor group's logits rows, the loader's read ring) count against one registration, and the last view dropped waits for its stream's copies and unregisters it at once rather than through the graves: HIP keys a registration by address, and one left behind after the caller freed its memory was taken for the next memory mapped there, whose copies faulted the device; HIP takes a second registration of a span and drops it at one unregister, so the count is the backend's, and a second span at a registered address, or one HIP refuses, gives no view, so the caller writes through staging; `write` and `read` go through a pinned staging ring, and host values a kernel reads (positions, ids, block tables) through an argument ring, each slot reused once the ticket that last read it retires. The values every layer of a pass reads alike, attention's block table, firsts and ends, the KV write's blocks and slots and the positions, go through `pass_arg`: the first layer to name a set copies it from the argument ring into a ring of device memory on the stream ahead of its launch, and a later layer whose set has the same bytes reads that copy, so the kernels read device memory and not pinned host memory over PCIe; the host compares and never waits for the copy, and a device slot is taken again only once the last launch that read it retires. A dropped buffer's memory waits in the backend's graves until the ticket covering the work recorded before the drop retires, since `hipFree` unmaps it at once even while a queued launch or copy names it: a model buffer dropped mid-prefill faulted a 16K prompt.
  - Errors: a call refused as it is enqueued throws at once; a failure the device reports at an event is kept as the first cause, which `raise(t)` before results are read in place, `read` and the next launch or submission throw.
  - KV: blocks of 64 tokens through the shared `BlockKVStorage`, F32 or F16 sides, with a layer's auxiliary F32 rows and pooled-row room in their own plane of the same blocks (`kv_alloc`'s widths and pools), which `kv_write` fills token-major through the storage's copies (`write_aux`), an old buffer a growth copied from dropped into the graves like any other.
  - Weight types: one descriptor row a type (`kTypes`), naming the F32 class's exact product, the embedding and the type's twin kernels (`TwinKernels`: its row builds by form and columns, the output rows a wave of each takes, its four-row builds and its tiles, tall or not), which every caller reads, so no caller switches on a type; `supports_type` is that table. F32, Q8_0, Q4_K, Q5_K, Q6_K, Q5_0, Q5_1, BF16 and IQ4_NL are in it, and Q8_0, Q4_K, Q5_K, Q6_K, Q5_0, Q5_1 and IQ4_NL have twins, IQ4_NL's grid values as signed bytes, sign-extended in the 16-bit words: BF16 takes its exact product in every class, wider than asked, as Vulkan takes its F32 rows, which `dtype_path` names from the table and the product records as the F32 path. `rocm_take_launches` gives the kernels launched since its last reading by name, the witness of which row build, tile or exact kernel ran. `rocm_profile` gives the profile the backend shapes its kernels by, which `kv-selection` reads and changes to run each selection form at one size.
  - Ops: `matmul`, `matmul_add`, `matmul_group` (one twin for the group's projections, kept for the next product of the same activations, which a launch writing only an exact product's, a router's or a grouping's outputs keeps unless it writes the twin's input, `launch_writing`) and through them `matmul_logits`, on the table's types: in the F32 class every type decoded exactly into F32 sums, in the F16 class Q8_0, the K-quants, Q5_0, Q5_1 and IQ4_NL on the block-int16 twin and in the int8 class on the block-int8 twin (`native_dtypes` {f16, f32, int8}, docs/PRECISION.md, section 5); `embed` of a table of any of them, at 64-bit offsets, and `embed_ids` through the same gather a type (`llmx_gather`, `llmx_gather_<type>`, which take the table's row count and write a +0 row for an id at or past it) with the ids read on the device, `argmax_rows` (`llmx_argmax_slices`, a block a slice of the profile's `argmax_slice` logits, then `llmx_argmax_merge` taking a row's slices in order on one lane, each step keeping the larger value, the lower id of equal values and a NaN or +inf flag, and refusing a row of no ids as Vulkan does), `gather_rows`, `rms_norm_rows`, `norm_rope_partial` over several rope streams, `gated_rms_norm`, `sigmoid_mul`, `causal_conv_silu`, `gated_delta_rule` (a block a view, V head and 32 V columns, in the Vulkan shader's order, so a sequence gives the same bits however its views are cut; the build staging 4 tokens where every view of the call holds at most 8 rows, as Vulkan chooses its short build, else the one staging 16), `norm_rope_kv`, `silu_mul`, `add`, `copy`, `kv_write`, `attention`, the Flash-Next stream and conv ops (`group_rms_norm`, `silu_scaled`, `mix_streams`, `inject_streams`, `signed_sqrt_gate`, `dilated_conv_silu_add`, in `kernels/f32.hip` at their Vulkan kernels' op boundaries and orders, F32 outputs, each row from that row alone and the conv's view in chunks of at least its history, so only a view's first chunk reads and leaves its carried raw rows), and the routed experts (`Op::routed_experts`): `route_experts` (a row a block of 64, its reductions the 64-pair tree, in the Vulkan kernel's order), `matmul_experts` and `matmul_experts_add`, each entry through its type's one-column body over its expert's rows (`llmx_routed_<type>` in the F32 class, the twin types' `routed16`, `routed8` and `routed_half8` builds in the others), so an entry gives the bits of its expert's one-column product; in the twin classes a call from its build's break-even (`TwinKernels::group_from`) groups them by expert (`llmx_moe_group`, the Vulkan grouping) and runs each group of up to 2, 4 or 8 entries, the narrowest holding their average, through the row build of that many columns (`routed16_g<C>`, `routed8_g<C>`, `routed_half8_g<C>`), a column an entry, whose twin column and outputs the build reads from the group (`EntryCols`), so each entry keeps its one-column bits and an expert's rows are read once a group; a prompt's rows from its build's tile extent for the call's role, gate and up or the down (`TwinKernels::tile_from`), take the routed tile instead (`routed_tile16`, `routed_tile8`): the grouping in groups of up to 64 entries, each group a block row of the prompt tile's 64 by 64 design over its expert's rows, or of its narrow build of 16 rows (`routed_narrow16`, `routed_narrow8`) where the group's entries fit them, both launched and each group running in one, never split, each entry's blocks summed in order in both, so an entry's sums are its own, the same in either build and within the tile's bound of its one-column product; and the down slots joined in slot order by `llmx_moe_combine`; `moe_step` is the base's sequence of them, with no fused step yet; and the indexer, `pool_kv` and `select_kv`, both pooling through one kernel (`llmx_kv_index_pool`), `select_kv` then scoring at most 16 rows at once (`llmx_kv_index_scores`) and selecting in one of two forms by the view's complete groups, the one-block selection (`llmx_kv_index_select`) below the profile's `select_wide_from` and from it the five-launch wide form over slices of 1024 groups (`llmx_kv_index_select_wide`), both by raw score bits with ties to the earlier group, so they give the same ids; and `sparse_attention`, each row over its selected ids, through the per-row attention body's sparse build for heads 128 and 256 wide (`llmx_sparse_attention_vec`, `llmx_sparse_attention_vec256`, the dense body's template with its head width a parameter) split in chunks of 256 ids and merged in split order (`llmx_sparse_attention_vec_merge`, `_merge256`), and through the chunk body's sparse build for other widths (`llmx_sparse_attention_chunk`, `llmx_sparse_attention_merge`), chunked by the id stride, so a row's splits follow the stride alone; an id outside the row's causal prefix is skipped and a row of none gives zeros. Every other weight type and named op is refused at load (`supports_type`, `implements`), `mixed_experts` among them, and `join` makes a tensor group's collective (`rocm_collective.hpp`, below).
  - Memory: `memory_available` is HIP's free device memory, and `scratch_reserve` leaves 256 MiB and a twentieth of it out of the fit, as Vulkan does, since HIP rounds each allocation to its pages (2 MiB past 1 MiB) and keeps memory of its own; without it a server fitted to the whole card ran out of memory as it allocated its cache.
  - Batch invariance: every kernel computes a row from that row alone in a fixed order. `row_class` makes a generated token one class; a prompt's rows are classed by the product tile's column tiles at their extent (`split_tiles_of`, up to 512 rows), which choose its inner split, by how many routed builds' tile extents (`TwinKernels::tile_from`) it reaches, which choose the routed tile, and by whether the extent reaches the profile's `attention_tile_rows`, which chooses the attention tile, so a choice follows the rows' prompt and never the rows a call holds.
- `rocm_collective.hpp`: a tensor group's collective (`RocmCollective`, docs/ROCM.md, step 4), which `rocm_backend.cpp` includes after the class; `join` takes two to sixteen ROCm devices of one kind, each once, led by the backend it is called on.
  - Fast path: each member's `llmx_group_sum` kernel (`kernels/f32.hip`), on that member's own stream behind the work that wrote its partial rows, pushes them into a staging slot in every peer's area, uncached memory from `hipExtMallocWithFlags` that a peer's stores reach without the fine-grain setting, releases an epoch into each peer's signal slot and waits on its own slots, then adds the members' rows in member order, its own from its partial rows and the others' from its staging, as `sum_rows.comp` adds them (t = p0, t += p1, ..., then residual += t, or residual = t in place), so the bytes are the Vulkan collective's. A second meeting after the sum keeps a member from writing a peer's staging for the next sum before that peer has read this one, so two sums may be in flight on one collective. Both phases take the same units of four floats in the same blocks, up to 16 blocks, each with its own slots for each of up to `backend::kMaxTensorWidth` members (`kGroupMembers`, the kernel's `GroupSignal` and `GroupPeers` sized by it and pinned by `static_assert`s on both sides; each member's `GroupPeers` is written once at join into its own device memory and passed by address, so the launch's arguments do not grow with the width), so a block's meeting covers exactly the rows it reads; the epochs live in the area, one a block, and skip 0 on the 32-bit wrap, since fresh slots hold 0.
  - Failure: a member's waits give up after one second of the device's wall clock (`hipDeviceAttributeWallClockRate`), or at once when a peer set the area's abort word; the kernel then leaves NaN where its sum would be, sets the abort word in every member's area, the collective's status word and its backend's fault word, both in pinned host memory. The fault word throws once at that backend's next check (`raise`, a launch or a submission), and the collective, which reads its status words in `wait` and before each sum, takes the conservative path for every later sum. A sum checks every member's failures before it launches on any, so no member waits for a peer whose launch threw.
  - Conservative path: each member records an event once its partial rows are written, pulls every peer's rows into its staging behind that peer's event, records a second event, and sums with the same kernel, in the same order, once every peer's second event says it has read its rows. It is taken from the start where `join`'s probe fails: a directed pair that cannot reach the other's memory, peer access refused, or one fast sum of known rows that gives other values or gives up.
  - The probe runs once per group of device indices, its answer kept by the first member, and its decision goes to stderr once (`rocm: tensor group of devices 0, 1 sums by peer writes`, or by peer pulls with the reason). `collective_bytes_per_row` counts a member's partial rows and a staging slot for each member, and `scratch_reserve` the 4 KiB signal block before them.
- `kernels/quant.h`: the one reader of block layouts on ROCm, the device counterpart of the Vulkan block decoders: for each type its values and bytes a block from `src/quant/types.hpp` and `value`, one value decoded with the CPU dequantizer's bits; `f32.hip` and `int16.hip` include it.
- `kernels/int16.hip`: the quantized products of the F16 and int8 classes (docs/PRECISION.md, rule 4 and section 5), reading the twin `kernels/f32.hip` writes: the Q8_0 row kernel for generated rows, which in the int8 class on rows of an even block count takes the Vulkan decode kernel's half-block order (`matmul_vec_q8_one.glsl`, `HALF`), two lanes a block, the even lane the scale and 16 weights and the odd lane the other 16, each as aligned words realigned in registers without a branch, the scale handed from the even lane to the odd, and four 8-bit dots against one 16-byte read of the twin, on the dot module where there is one, and otherwise the quarter layout, four lanes a block, a wave taking two or four output rows by the call's rows (`row_build`): the builds of two to eight columns take four once the call launches the profile's `row_four_waves_per_cu` waves a compute unit at four rows a wave and two below it, the F16 class's one- and sixteen-column builds two, the int8 quarter layout's one-column build two and its sixteen-column build four, the half-block order's sixteen-column build four, each twin load serving every row of the wave and each row keeping its lanes and order; the builds of four columns and more load the twin a group of columns at a time ahead of the group's products, a column past the call reading column 0 and storing nothing (skipped in the half-block order), and a build wider than its group addresses every column from one 32-bit lane offset rather than a pointer a column; a build of one group issues the weights' and the twin's loads before a scheduling barrier, ahead of any wait on them; every (row, column) sum of a wave is folded by one transposed xor tree (`wave_sums`), each level halving the values a lane holds, a lane keeping the half its partner bit selects and adding the partner's copy, so each sum has the bits of one butterfly tree and is written by its own lane, which takes its row's output from the wave's rows in scalar registers; a wave of fewer lanes than a build's sums, a 32-lane wave under the int8 class's 64-sum sixteen-column builds, folds them in parts of 32, each part the same tree; the lane exchanges by DPP and swizzles where the partner allows and a permute only across the wave's halves; the one-column build of the half-block order issues four steps of a lane's loads before their products, held together by a scheduling barrier, skips a step past the row in its loads and its product alike, so a lane's blocks keep their order by skipping rather than by adding zeros, and sums each row in the same order as the wider builds; a row of at most 16 blocks takes a 64-lane wave's halves as two rows (`llmx_q8_0_half8_1p`), each half's tree from 16 lanes giving the one-row build's bits since its lanes past the row hold +0, and from the profile's `q8_decode_two_rows_from` output rows the other one-column rows take two rows a wave (`llmx_q8_0_half8_1r2`), each twin load serving both, again the one-row build's bits; both rules read the row width, the output count and the type, never the call's columns; up to 16 columns a launch reading each weight once, a group's projections in one launch with their rows one after another (`RowCall`), in a loop over its rows (that form measured four times faster than an early return on some row counts); and the prompt tile.
  The prompt tile takes the Vulkan tile's design (`matmul_tile_q.comp`): 256 threads, 64 outputs by 64 rows, each thread 4 adjacent outputs by 4 adjacent rows, the blocks of a step (four for block-int8, two for block-int16) staged k-major in shared memory with the weights widened to the twin's integer type, four threads a twin row and 256 / outputs threads a weight row (four, or two on the tall build). A step's weights load as aligned 4-byte words realigned in registers, since a Q8_0 block is 2-byte aligned: a thread's share of a block, a quarter or a half, as one vector load of its words and one word more, the word before or after by its alignment, the scale taken from them. Every load of a step goes out before any is waited for, out-of-range ones at a valid address with their zero chosen at the store, each at a 32-bit byte offset off the tile's first output or row held in scalar registers (`at`), with no 64-bit address arithmetic, and the next step loads while the current one computes. Buffers are allocated in whole words, since the last word of a final block may run past it. A thread reads its outputs' and rows' word as two 16-byte reads and feeds 16 integer sums; each output sums its blocks in order, acc = fma(dw * dx, isum, acc). A tall build of 128 outputs, each thread 8 outputs by 4 rows, two blocks a step in both classes, the block-int16 one loading its step after the barrier rather than while the previous step computes, sums each output in the same order and keeps the 64-output build's inner split, so a call takes it by the device profile's `tile_rows_for` without a change of bits; the MI50's HIP row takes it on rows from 4096 wide at 6 workgroups a compute unit (docs/STATUS.md, ROCm tall tile).
  The twin products of the K-quants, Q5_0, Q5_1 and IQ4_NL (`k_rows`, `k_tile`) read their blocks through one raw load and decode a type (`KRaw`): a lane, or a tile thread, takes eight values of one 32-value sub-block, the twin's block, as two words of bytes, unsigned but for IQ4_NL's signed grid values, with the sub-block's scale and min, widened to 16-bit pairs for the block-int16 twin by a byte permute or, for IQ4_NL, a sign extension; a sub-block's term is ds * (q . x) - dm * sum(x) over the twin's exact integers, Q6_K's offset of 32 and Q5_0's of 16 taken out of the integer sum and Q5_1's min added as a negative dm, every fused step written as fmaf. The row builds (`k_rows`, one body for the dense, routed and grouped builds) take one, two, four, eight and sixteen columns at two rows a cluster in the Vulkan row layout (`matmul_row_one.glsl`): a row takes a cluster of lanes, the power of two covering its lane units up to the wave and, for Q4_K and Q5_K, the profile's `k45_row_lanes` (`row_cluster`), a wave holding warpSize / cluster clusters; a type's lane (`KRaw`'s `Lane`) loads its share of a block, Q4_K and Q5_K eight lanes a block of two 16-value runs each, Q6_K sixteen lanes of 16 values, Q5_0 and Q5_1 one lane a block of 32 values, and the quarter form (`QuarterLane`) four lanes a block of 8 values through the type's own raw load and decode, the tile's arithmetic; IQ4_NL's rows take the quarter form alone, since one lane decoding 32 grid values measured slower at 640 and 2560 values wide, and a Q5_0 or Q5_1 row takes the quarter form where its lane units fill the cluster's steps fuller than one lane a block, one lane on a tie (`row_form`; on a 64-lane wave 640 and 1024 wide one lane, 2560 and 1056 the quarter form); each lane adds its runs' terms in block order and the cluster folds them by one xor tree (`store_cluster_sums`), transposed where the cluster has a lane for every sum; the cluster and the form follow the row's width and type alone, so a row and every routed or grouped entry of it give the same bits; the tile is the Q8_0 tile's 64 by 64 design and staging of the twin, its weight rows decoded as they are stored to shared memory, each output summing its blocks in order, acc = fma(dx, term, acc); Q6_K, whose scale changes every 16 values, takes a sub-block as two halves (`halves` of `KRaw<rq::Q6_K>`), each with its own scale, integer dot and term. Neither has a four-row or tall build yet.
  The tile reads its twin block-major: the backend lays the twin out from the call's runs (`TwinMap`, one place, which the twin's producers and the products share), a run of generated rows row after row as the row kernels read it, a prompt's rows with block k of every row of its region together and the rows padded to an odd multiple of 4, so a stage's rows are one coalesced read and block k + 1 starts on other memory channels than block k; neighbouring runs of one kernel share a region, and neighbouring runs of generated rows, or of prompts of one inner split, share their launches, so a decode pass of four sequences reads each weight once; a call of more regions than the map's eight lays every row row after row, which the tile reads through its row and block strides as well. It moves where a value lies, never a value, so the bits are the same either way (docs/STATUS.md, ROCm block-major twin). Each twin producer has a map-free build, which a call whose twin lies row after row takes, and a build reading the map (`_major`), so decode runs no code of the map.
  A call of up to three projections of one X takes one tile dispatch (`TileCall`, whose host copy a `static_assert` pins), and the inner dimension splits into parts by the Vulkan tile's rule (`split_blocks`, the device profile's workgroups per compute unit) for the column tiles of the rows' prompt, not of the call; `llmx_tile_reduce` adds the parts in order.
  Every kernel here declares its 256-thread block (`__launch_bounds__`), since the compiler's default assumes 1024 threads, caps a thread at 64 registers and spilled the tile's prefetch to scratch.
  A row kernel finds an output row's projection (`row_of`) by adding the differences of the projections' fields under two comparisons, since a select between the fields compiled to an indexed load that kept each routed and grouped build's modified copy of the call in scratch, 120 bytes a lane on gfx906, which took a routed call at Flash-Next's shapes three to four times as long (docs/STATUS.md, ROCm routed decode); the addresses are the same, so the bits are.
  The file is compiled twice: as the int16 module for every target, and with `LLMX_DOT16` for gfx906 alone as the dot module, whose word dots run on the 16-bit and 8-bit integer dots (`__builtin_amdgcn_sdot2`, `__builtin_amdgcn_sdot4`). The backend loads the dot module where the build holds a code object for the device, and that load is `DeviceCaps::integer_dot`, read from the code object and not from the device's name. The prompt tile and the row kernels of four columns and more then come from the dot module, while the one- and two-column quarter-layout builds stay on the int16 module, which measured faster there; the integer sums are exact, so both modules give the same bits.
- Contraction: every kernel compiles with `-ffp-contract=off` (`LLMX_HIP_FLAGS` in `CMakeLists.txt`), since whether HIP fuses `a * b + c` depends on the product's other uses after inlining, which differ between the builds of one body; the order of each kernel (op boundaries, tiles, splits and merges) follows the Vulkan design, and every multiply-add accumulation is written as `fmaf`, attention's online softmax `l`, its score dots and the merges' `L` and `A` among them, so the bits hold between ROCm's own builds and classes; across backends ROCm is held to the CPU's bound and to HF, not to Vulkan's bits.
- `kernels/f32.hip`: the dense F32 kernels, compiled at build time to a code object for gfx906 and gfx1151 (compile coverage only) and embedded as a byte array (`cmake/embed.cmake`), as the Vulkan SPIR-V is. Every sum is F32, folded by one block tree whatever the wave width, its levels across waves in shared memory and the rest by shuffles that add the same pairs. The twins of the quantized products' activations are made here, at 32767 levels for block-int16 (`llmx_twin16`) or 127 for block-int8 (`llmx_twin8`), by the rule in STATUS, and, as the Vulkan producers write them, by `rms_norm_rows`, `silu_mul` and the per-row attention (at one split, else its merge, when no row of the call takes the tile) beside their outputs once a product has read a twin in that class, laid out from the runs they are given (the attention from its views) as the product of those runs lays it: the backend keeps the twin's tag, and a product of that output reads it instead of making its own, while any other launch, copy, write or allocation drops it. Norm rows of up to 8192 values take a block of 1024 threads that load the row and its weights at once and each scale and twin a quarter of what a 256-thread block's would, the sum chained by 256 of them in the plain kernel's order, which serves wider rows; a decode row is one block, so the work a thread does in sequence is its time. Attention splits each row's history into chunks of its own, at 256 positions each and at most 16, each chunk an online softmax over 64-position tiles in order, then merges the chunks in order; the split depends on the history alone, so a row gives the same bits in any call. A prompt's view whose extent reaches the profile's `attention_tile_rows`, causal and of 128-wide heads, takes `llmx_attention_tile`, the Vulkan attention tile's design (`attention_tile.comp`): a block a tile of 32 query rows of one view and one head, eight lanes a row holding 16 dimensions of the scaled query, K and V through shared memory 16 tokens at a time, scores as partial dots folded by a butterfly over the row's lanes and a per-row online softmax over the row's whole history from token 0; a row depends on its own history alone. Generated rows and shorter prompts of 128-wide heads, and every row of 256-wide heads, take `llmx_attention_vec` (`llmx_attention_vec256` at 256, its split bounded by `attention_split_max_wide`), the Vulkan per-row attention's design (`attention_vec.comp`): a block a (row, head, split), 16 streams of 16 lanes each taking every 16th token of the split, a lane 8 dimensions, an online softmax per stream and the streams merged in order; a row's splits are chunks of its own length (the profile's `attention_split_chunk`, doubled until at most `attention_split_max` parts), so it computes the same beside any rows, and `llmx_attention_vec_merge` (`_merge256`) adds the splits in order. Other head widths keep the chunk kernel. `norm_rope_kv` is one launch a layer (`llmx_norm_rope_kv`): q's and k's heads normed and rotated in place by the device function `llmx_norm_rope` holds a head with, and k and v written into their KV blocks as `llmx_kv_write` writes them; a head wider than a block, or k's rows not dense, takes the ops one at a time. Every kernel skips a tile row, marked by an end of 0. The exact products and embeddings of the other types (`llmx_matmul_<type>`, `llmx_gather_<type>`) decode each value through `kernels/quant.h`, as the F32 product sums: an output's sum is 256 strided chains, lane l's over values l, l + 256 and so on in order, folded by the block tree. One row takes a wave an output (`exact_wave`), each lane holding 256 / warpSize of those chains side by side, so its loads are whole: F32 and BF16 rows read four weights at once where they are aligned, and the steps every lane fills are unrolled so their loads issue ahead of the chains; the tree's levels from the wave's width up are shuffles and those below it adds in registers, the same pairs, so an output keeps the bits of the block an output it replaced; the routed F32 class's entries (`llmx_routed_<type>`) run the same body. An F32 call of two to four rows takes `llmx_matmul_cols2_f32` or `llmx_matmul_cols4_f32` (`exact_cols`), a wave an output that reads its weight row once and keeps each row's chains, so every output has the bits of its one-row product; a verify of three drafts would otherwise take the 8-row block for four rows. Any other call of more than one row takes `llmx_matmul_rows_<type>`, a block of 8 outputs by 8 rows whose lanes keep the same strided chain for each output and row and fold each by the same tree, so every output has the bits of its one-row product while a weight row is read once for 8 rows and an activation row once for 8 outputs. ## Kernel notes

What the kernels' comments leave out, file by file and in file order: their layouts, their orders of work and why they take them.

`kernels/f32.hip`:

- The dense F32 kernels of the ROCm backend (docs/ROCM.md, Delivery checkpoints, step 2) and the activation twins the quantized products read: every sum is F32 in a fixed order that depends on the row alone, never on how many rows a call holds.
  A block reduction folds lane partials in one tree whatever the wave width, so a row gives the same bits in any call.
- A block a row of n <= K * kThreads values: dst = RMSNorm(src) against w, with its twin at L levels beside it when L is not 0, the rows then dense and n a multiple of 32.
  Each of the block's kNormThreads threads loads its values and their weights at once, element t + kNormThreads j; the sum is rms_norm_row's, thread t < kThreads chaining elements t + kThreads k and the chains folded by block_sum's tree, so both give the same bits.
- Member `rank`'s part of a group sum of n floats: out = the members' rows added in member order (flag 1), or out += them.
  Fast (flag 2): push its own rows into every peer's staging, meet, sum, and meet again before a later sum may write a peer's staging; otherwise the host has pulled the peers' rows into its staging.
  Both phases take the same units of four floats in the same blocks, so a block's meeting covers exactly the rows it reads; a failed meeting before the sum leaves NaN in out.
- A block a (row, head, chunk) of the split attention: 64 positions a tile, four threads a position's dot and one thread a dimension's accumulator, an online softmax over the chunk's tiles in order.
  The chunk's maximum, sum and accumulators go to `part` for llmx_attention_merge.
  SPARSE reads the row's `stride` selected ids in place of its positions, chunked by the stride alone, an id outside the row's causal prefix (`ends`) skipped.
- Causal attention of a prompt's rows (the Vulkan tile's design, attention_tile.comp): a block a tile of 32 query rows of one view and one head, eight lanes a row each holding 16 dimensions of the scaled query, K and V through shared memory 16 tokens at a time.
  A row's scores are partial dots over its lanes folded by a butterfly, its softmax runs online over the tiles from token 0 in order, so a row's result depends on its own history alone, whatever rows share its tile; heads 128 wide.
  `views` holds, a view each, its first row, rows, history, first block in `table` and first tile; `tiles` is their total.
- Causal attention of rows that attend one at a time (the Vulkan per-row design, attention_vec.comp), heads DIM wide, 128 or 256: a block a (row, head, split), streams of DIM / 8 lanes, each stream's softmax online and the streams merged in stream order.
  A row's splits are chunks of its own length; one split writes O and its twin (twin_at), several write partials for llmx_attention_vec_merge; a row whose end is 0 is the tile kernel's.
  SPARSE reads the row's `stride` selected ids in place of its positions, split in chunks of `chunk0` ids, a function of the stride alone; an id outside the causal prefix is skipped and a row of none gives zeros.
- The linear attention's causal conv of four taps, then SiLU (backend.hpp, causal_conv_silu), a thread a channel of a chunk of up to `chunk` rows of one view, as the CPU's multiply and fused multiply-adds in tap order, so a row is the same however its view is cut.
  tab holds the view count, five words a view (first row, rows, history length, source slot, destination slot), then two a chunk (view, first row); a view's first chunk reads its carried rows before it leaves its last three raw rows in slot dst.
- The gated delta rule (backend.hpp, gated_delta_rule) in the Vulkan shader's order (shaders/delta_rule.comp): a block a (view, V head j, 32 V columns), eight lanes a column holding 16 K rows each, q and k L2-normed and the gates made for each 16 tokens, every sum a lane's fused multiply-adds then lanes8.
  A sequence gives the same bits alone, batched or cut into passes; the decay is 0 below 2^-126. tab is causal_conv_silu's view table.
  The decode build stages 4 tokens a barrier and the prompt build 16; a token's decay is applied in the token before it or at its stage's start, the same products in the same order, so the two give the same bits.
  Both are bounded to 256 threads and two waves a SIMD, so a lane holds its 16 state rows in registers (127 VGPRs on gfx906); without a bound the compiler budgeted for 1024 threads, kept the rows in 304 bytes of scratch, and a one-row call took 74 us against 25 (docs/STATUS.md, ROCm decode steps 2 to 6).
- The Flash-Next stream ops (backend.hpp), each at its Vulkan kernel's op boundary and in its order (shaders/group_rms_norm.comp at fc6f53415, silu_scaled.comp, mix_streams.comp and inject_streams.comp at ca0f1f7df, signed_sqrt_gate.comp and dilated_conv_silu_add.comp at 7184ff13f), every value a function of its own row, the transcendental steps with expf.
  `llmx_signed_sqrt_gate` takes the sign 0 at a zero dot, or with its `kept` argument (`ZeroSign::kept`) the zero's own sign through `copysignf`.
  `group_rms_norm`, `silu_scaled` and `mix_streams`, and the gate ops `sigmoid_mul` and `gated_rms_norm`, write their output's twin beside it (twin_at) where the host asks for one: an output of whole blocks a row that a product reads next, at that product's class and map, so the product takes it without a twin launch; the map is read in place, since a pointer chosen at run time between it and null kept it in scratch.
- A block a (row, group) and slice of rows of groups * dim values: the group's RMS norm against its own dim weights, each thread's squares of values t, t + 256, ... in order, then block_sum's tree, slice y of gridDim.y writing the group's 1024-value chunks y, y + gridDim.y, ...
  Every slice repeats the whole reduction, so a group's bits do not depend on its slices; dst may be src with one slice, since every value is read into the sum before the block's barrier.
- A block a (row, group): g = dot(key, query) * scale over the group, each thread's products of values t, t + 256, ... in order then block_sum's tree, and the row's dim values times sigmoid(sign(g) sqrt(max(|g|, 1e-6))), a NaN score kept as the CPU keeps it.
- The dilated causal conv of `taps` taps `dilation` rows apart, its SiLU and the residual added (backend.hpp, dilated_conv_silu_add), a thread a channel of a chunk of up to `chunk` rows of one view, the first tap a multiply and the rest fused multiply-adds in tap order, so a row is the same however its view is cut.
  tab is causal_conv_silu's; the (taps - 1) * dilation raw rows a view carries sit `prefix` floats into its slot, and chunk is at least that history, so only a view's first chunk reads them, before it leaves the view's last raw rows in slot dst in ascending order, which reads an old row before a lower row of the same slot is written.
- A row's routing (llmx_moe_route), a block of 64 a row: its softmax, top-k picks and their sum, each reduction the 64-pair tree, lane t adding lane t + s at level s, the levels below the wave's width by xor shuffles and those at or above it through shared memory, so a row's picks and weights are the same on 32- and 64-lane waves; a pick is the largest (value, lowest id) pair, a total order, so one reduction gives both.
- y[r * n + o] += sum over j in order of weights[r * k + j] * part[(r * k + j) * n + o], a routed down projection's slots joining the residual (backend.hpp matmul_experts_add), in Vulkan's order (moe_combine.glsl): slot 0's product is the sum, each later product is rounded, then added; a slot without an expert adds nothing.
- A grouped routed call's groups (the Vulkan grouping, moe_group.comp), a block an expert: tab holds max_groups groups as (expert, first, count, 0), each at most `chunk` entries of one expert and unused ones of count 0, then from word 4 * max_groups the entries in expert order, entry order within an expert.
  The grouping orders the work only: an entry's outputs are its one-column product in any group.
- A block scores eight groups of tile blockIdx.x for query row blockIdx.y, 32 lanes a group: each head's dot over slots lane + 32 c in order, then a butterfly over the 32 lanes, the heads' rectified dots summed in turn, a NaN dot kept as the CPU keeps it.
  Row r sees (hist + r + 1) / compression groups, its scores a row of `stride` apart.
- The id of each row's largest logit, ties to the lowest (Backend::argmax_rows): a block a (row, slice of `slice` ids) reduces its slice, a NaN or an infinity there making the slice's value NaN; with one slice it writes the id, else its value and id for llmx_argmax_merge.
  A row is `n` where a slice saw a NaN or an infinity, its largest is -inf, or its id in `after`, when given, is `n` or more.
  Every step keeps the larger value, the lower id of equal values, and ORs the flag, so the id is the CPU's in any reduction order; the merge takes the slices in order on one lane.

`kernels/int16.hip`:

- The int8 class's Q8_0 decode kernel in the half-block order of the Vulkan decode kernel (matmul_vec_q8_one.glsl, HALF), for rows of an even block count: a wave R output rows, two lanes a block, so a wave reads warpSize / 2 blocks a step.
  The even lane takes the block's bytes [0, 18), the scale and 16 weights, the odd lane bytes [18, 34), each as aligned words realigned in registers without a branch, and the even lane hands the scale to the odd one; a branch on the alignment waited on its loads and measured slower (docs/STATUS.md, ROCm decode products).
  Each lane scales its halves' integer dots into F32 in block order and the lanes fold by the transposed tree of wave_sums, the bits of one shuffle tree for every column whatever C and R the call takes.
- A routed tile call's groups (kernels/f32.hip, llmx_moe_group): group first + blockIdx.y a tile of its expert's rows, its columns its entries, entry e reading twin row e / per and writing output row e, projection p's experts stride[p] bytes apart.
  The call never splits, so an entry's sums do not depend on the entries beside it.
- Blocks of 32 staged a barrier, as the Vulkan tile stages them: four for the 8-bit twin, two for the 16-bit one, whose widened words are twice as many.
  A step loads while the previous one computes, but in the tall build over the 16-bit twin, which loads its step after the barrier: holding the next step's loads took it 124 VGPRs and after the barrier it takes 99 (docs/STATUS.md, ROCm tall tile staging).
  A value at a 32-bit byte offset from a uniform base, so the load takes the base from scalar registers and the offset from one vector register, with no 64-bit address arithmetic; the host bounds every offset (`rocm_backend.cpp`, the tile launch).
- The prompt tile (the Vulkan tile's design, matmul_tile_q.comp): a block of 256 threads 64 outputs by 64 rows, each thread 4 adjacent outputs by 4 adjacent rows, the blocks of a step staged k-major in shared memory, word w of every output and then of every row, the weights widened to the twin's integer type.
  A thread reads its four outputs' word and its four rows' word as two 16-byte reads and feeds 16 integer sums; each output sums its blocks in order, acc = fma(dw * dx, isum, acc), so a row gives the same bits wherever the tile falls.
  Routed (TileGroups), a block row is a group: its rows are its entries and its weights its expert's.
  The narrow build (a group of up to 16 entries) gives each wave one quad of the group's entries over all 64 outputs, a thread one output by four entries, rotated by workgroup since wave w runs on SIMD w, and a wave whose quad holds no entry skips its dots, as the Vulkan narrow build's column quads do; every entry keeps its integer block sums and float terms in block order.
- A thread's quants sit at an offset of 0 or 2 in their 4-byte words, since a block is 34 bytes: one vector load of WQ words and one word cover them, the word after where they straddle and the word before where not, which holds the scale in its high half; straddling, the first word holds it in its low half.
  Every load of a stage goes out before any is waited for: a load out of range reads block 0 and its zero is chosen at the store, so no load sits under a branch the compiler would wait inside.
- The twin products of the K-quants, Q5_0, Q5_1 and IQ4_NL: a lane, or a tile thread, takes eight values of one 32-value sub-block, the twin's block, as two words of bytes, unsigned but for IQ4_NL's grid values and the sub-block's scale ds and min dm.
  A sub-block's term is ds * (q . x) - dm * sum(x) over the twin's integers, Q6_K's offset of 32 taken out of the exact integer sum, every fused step written as fmaf, the kernels compiling without contraction (CMakeLists.txt, LLMX_HIP_FLAGS).
- The K-quants' prompt tile: q8_0_tile's 64 outputs by 64 rows and its staging of the twin, each weight row's twin block staged by four threads as its eight-value parts, widened to the twin's words, with the scale and min of each of the sub-block's H halves.
  Each output sums its blocks, and a block its halves, in order, acc = fma(dx, term, acc), so a row gives the same bits wherever the tile falls.
- Every kernel here runs blocks of kThreads, which __launch_bounds__ tells the compiler: its default assumes 1024 threads and caps a thread at 64 registers, which spilled the tile's prefetch to scratch.
  The row kernel's builds, the host taking the narrowest that holds a call's columns.
  R is the output rows a wave takes and G the columns whose loads issue together; a build named _r4 takes four rows where its namesake takes two, the host choosing between them by the call's rows (rocm_backend.cpp, row_build).
