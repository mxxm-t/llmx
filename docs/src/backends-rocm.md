# `src/backends/rocm/` - the ROCm backend

The ROCm backend over HIP ([ROCM](../ROCM.md)), built only with `LLMX_HAS_BACKEND_ROCM` on Linux, in progress as step 2 of that plan: dense F32 models on one device.

- `rocm_runtime.hpp`: the HIP runtime opened at run time with `dlopen`, its calls in one table (`hip()`) loaded by their exported names, so a build with the backend still runs where no ROCm is installed; a test substitutes a call in it to inject a failure. A missing library, call or device throws `RocmUnavailable`, which the caller reports as a missing device. `hip_check` turns a failed call into a runtime error naming the call and the runtime's reason.
- `rocm_device.hpp`: a device as HIP reports it (`rocm_device(index)`): its wave width, compute units, name and runtime version in `DeviceCaps` ([device_profile](backends-device_profile.md)), and beside them its ISA, memory, PCI address and root complex (`pci_root_of`).
- `rocm_backend.hpp`: `make_rocm_backend(index)`, the one entry the device factory ([devices](backends-devices.md)) reaches for `--device rocm:N`.
- `rocm_backend.cpp`: the backend, a translation unit of its own as the Vulkan backend's is.
  - Execution: one non-blocking HIP stream a device, every op an asynchronous launch on it; `submit()` records an event from a ring of 1024 and returns its ticket from the shared `TicketLedger` ([backend](backends-backend.md)), and a slot is reused only once its earlier ticket has retired. `wait` synchronises on the ticket's event and `done` queries it.
  - Products into host memory (the logits): a product whose output is pinned host memory is formed in device memory and copied over whole, since the row kernel's one float a row over PCIe took the 0.6B's head 3.3 ms of a token.
  - Memory: `alloc` is device memory zero-filled on the stream, or pinned host memory the device reads in place (`Memory::host_visible`); `write` and `read` go through a pinned staging ring, and host values a kernel reads (positions, ids, block tables) through an argument ring, each slot reused once the ticket that last read it retires. A dropped buffer's memory waits in the backend's graves until the ticket covering the work recorded before the drop retires, since `hipFree` unmaps it at once even while a queued launch or copy names it: a model buffer dropped mid-prefill faulted a 16K prompt.
  - Errors: a call refused as it is enqueued throws at once; a failure the device reports at an event is kept as the first cause, which `raise(t)` before results are read in place, `read` and the next launch or submission throw.
  - KV: blocks of 64 tokens through the shared `BlockKVStorage`, F32 or F16 sides, an old buffer a growth copied from dropped into the graves like any other.
  - Ops: `matmul`, `matmul_add`, `matmul_group` (one twin for the group's projections) and through them `matmul_logits`, on F32 and Q8_0 weights: in the F32 class Q8_0 decoded exactly into F32 sums, in the F16 class (`native_dtypes` {f16, f32}) Q8_0 on the block-int16 twin; `embed` of an F32 or Q8_0 table, `gather_rows`, `rms_norm_rows`, `norm_rope_partial` with one rope stream, `silu_mul`, `add`, `copy`, `kv_write` and `attention`. Every other weight type and named op is refused at load (`supports_type`, `implements`), and `join` keeps the default, so tensor groups are refused until step 4; the routed products (`Op::routed_experts`) are among the refused ops, so a routed layer stays on a host that runs them.
  - Memory: `memory_available` is HIP's free device memory, and `scratch_reserve` leaves 256 MiB and a twentieth of it out of the fit, as Vulkan does, since HIP rounds each allocation to its pages (2 MiB past 1 MiB) and keeps memory of its own; without it a server fitted to the whole card ran out of memory as it allocated its cache.
  - Batch invariance: every kernel computes a row from that row alone in a fixed order, so `row_class` makes a generated token one class and every prompt row another.
- `kernels/int16.hip`: the F16 class's quantized products (docs/PRECISION.md, rule 4): the block-int16 twin of a call's activations (`llmx_twin16`, the rule in STATUS), the Q8_0 row kernel for generated rows, a wave an output row folded by one shuffle tree, up to 16 columns a launch reading each weight once, and the prompt tile, 16 outputs by 16 rows a block, each output summing its blocks in order; integer block dots, F32 sums. A run of generated rows takes the row kernel and a prompt's rows the tile, never by the call's width, so a row gives the same bits in any call. The file is compiled twice: as the int16 module for every target, and with `LLMX_DOT16` for gfx906 alone as the dot module, whose block dot runs on the 16-bit integer dot (`__builtin_amdgcn_sdot2`). The backend loads the dot module where the build holds a code object for the device, and that load is `DeviceCaps::integer_dot`, read from the code object and not from the device's name. The prompt tile then comes from the dot module, while the row kernels stay on the int16 module, which measured faster there; the integer sums are exact, so both modules give the same bits.
- `kernels/f32.hip`: the dense F32 kernels, compiled at build time to a code object for gfx906 and gfx1151 (compile coverage only) and embedded as a byte array (`cmake/embed.cmake`), as the Vulkan SPIR-V is. Every sum is F32, folded by one block tree whatever the wave width. Attention splits each row's history into chunks of its own, at 256 positions each and at most 16, each chunk an online softmax over 64-position tiles in order, then merges the chunks in order; the split depends on the history alone, so a row gives the same bits in any call. A call holding a prompt's rows on F16 sides of heads up to 128 wide runs the chunks in `llmx_attention_tile`: a block takes up to 16 of a view's rows that share one split, with the query heads of one KV head (32 pairs at most), reads each 64-position tile of K and then V into shared memory once for all of them, and forms every pair's scores, trees and accumulators with the chunk kernel's operations in its order, so a row's bits are the chunk kernel's. Generated rows alone keep the chunk kernel, whose blocks of one row and head fill the device better.

`rocm-runtime` (CTest) opens device 0, checks the facts it reports, round-trips 4 MiB from pinned host memory to the device and back on one stream with an event, and checks that an allocation past the device's memory is refused by name. `backend-rocm` checks the backend's buffers, a 256 MiB buffer dropped with 64 copies out of it queued among them, tickets and refusals and holds each op to the CPU backend and to its own rows alone. Both exit 77 without a runtime or a device.
