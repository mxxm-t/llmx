# `src/format/file_reader.hpp` - a file read at given offsets

`format::FileReader(path, direct = false)` opens a file for reading at offsets into the caller's memory, by several threads at once, through the file cache or, with `direct`, around it; the loader streams every weight it does not map through it in large reads in file order ([load](inference-load.md)), where a mapping would fault them in a page at a time inside the upload's copy.

- `read(offset, dst, bytes)` reads up to `bytes` from `offset` and returns how many it read, fewer only at the end of the file; a read at or past the end returns 0. Errors throw `std::runtime_error` naming the file.
- `size()` is the file's size when it was opened, and `path()` its UTF-8 path.
- `granule()` is the unit a read starts and ends on: for buffered reads the larger of the page (`core::page_size`) and the file's block size (`st_blksize`), which on ZFS is the dataset's recordsize, and the page on Windows; for direct reads the alignment the file system requires, at least a page.
- `direct()` says which it reads. A direct read must start and end on `granule()` and land on a page; one that does not throws `std::logic_error`, since ZFS 2.4 serves a misaligned direct request through its cache rather than refusing it. A read rounded up past the end comes back short by what the file lacks.
- `DirectUnavailable`, a `std::runtime_error`, is what opening for direct reads throws where the file system does not take them.

On Linux and macOS it opens the file `O_RDONLY | O_CLOEXEC`, advises sequential access where `posix_fadvise` exists unless the reads go around the cache the advice is for, and reads with `pread` in a loop that retries on `EINTR`, so reads at different offsets share the descriptor safely. One call reads at most 1 GiB, a multiple of every granule, since Linux cuts a larger request short at a length a direct read cannot take and macOS refuses one over 2 GiB.
On Windows it opens the file from its UTF-8 path with `CreateFileW` (`FILE_SHARE_READ`, `FILE_FLAG_SEQUENTIAL_SCAN | FILE_FLAG_OVERLAPPED`) and reads with `ReadFile` on an `OVERLAPPED` at the offset, each call with its own event, since the handle's own signal is shared by every read in flight on it; `GetOverlappedResult` waits for it, and `ERROR_HANDLE_EOF` is the end of the file. One call reads at most 1 GiB, and `read` loops.

Direct reads on Linux open the file `O_DIRECT` and read the alignment from `statx(STATX_DIOALIGN)`, called by raw syscall with the kernel's struct layout (`KernelStatx`) whatever the C library declares; a kernel without it (before 6.1), a file system that reports no alignment (ZFS with `direct=disabled`) or one that refuses `O_DIRECT`, and a memory alignment above a page, are refused. The granule is the larger of the page and the offset alignment, the recordsize on ZFS.
On Windows direct reads open the file `FILE_FLAG_NO_BUFFERING`, take the granule from the larger of the page and the logical and physical sector sizes `GetFileInformationByHandleEx(FileStorageInfo)` reports, and make one aligned probe read at open, whose failure refuses them. Other systems refuse direct reads.

Buffered reads go through the operating system's file cache, so a model read once is served from it again while the host has room; `tests/file_reader.cpp` (CTest `file-reader`) checks the reads on a file of several granules, the short read at the end, empty and tiny files, and concurrent readers; where the file system takes direct reads, aligned ranges, a read rounded up past the end short by what the file lacks, and misaligned requests refused, and where it does not, a refusal naming the file.
