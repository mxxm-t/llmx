# `src/inference/load.hpp` - loading a model file

`LoadedModel::dtype` retains the policy record returned by placement. Loading does not independently choose precision; the placed model has already received the same policy for execution.

The one sequence that turns a model file into a model ready to run, in namespace `infer`.
The CLI's commands that run a model, `llmx-split-check`, `llmx-decode-probe`, `llmx-model-logits`, `llmx-multi-device-bench` and `compare_cpu` all load through it, and none of them repeats its steps.

- `LoadMode { automatic, mapped, direct }`, `load_mode_of(name)` and `load_mode_name(mode)`: how a load reads the weights, the CLI's `--load-mode` (`auto`, `mapped` or `direct`), the same on every backend; the first is the default, which the CLI's `ExecOptions` and `load_model` both take from `LoadMode{}`. An unknown name throws.
- `--lookup-storage` (`LookupStorage`, [place](model-place.md)) is a separate choice carried by `PlacementRequest`, which applies only to immutable lookup tensors an architecture declares; models without such tensors keep their ordinary weight path.
  A table read from its file reads its rows on its own readers in every mode, through the file's buffered reader in `automatic` and `mapped` and its direct reader in `direct`; it is never mapped and never joins the stream or the warming.
- `LoadStep` and `LoadReport`: what a load is doing, for its caller to show: the phase it is in, `metadata`, `fit`, `allocate` or `weights`, and in `weights` the bytes read of the bytes it reads, of every file and of the file its last read was from; `load_model` reports each phase as it begins and the weights' bytes as they are read, which the CLI's bar and the server's startup record ([server](server.md), `Startup`) take.
- `LoadTimes`: where a load's time went, for the CLI's timing line: the mode, the files the weights were streamed from through the file cache (`files`) and around it (`direct_files`), the bytes read for them and those the devices copied straight out of the reads (`copied`), and the seconds spent building the model (`construct`), in the busiest reader thread's reads (`read`), in the uploads (`upload`) and in the uploads' waits for a read (`wait`).
- `LoadedModel`: what a load gives its caller.
  - `file` is the `gguf::GGUFModel` whose payload a host backend reads in place while the model lives, unless the load was direct.
  - `tok` is its tokenizer.
  - `chat` is its `chat::ChatFormat` (`chat::chat_format`), which `chat` and the server render conversations with.
  - `plan` is what each device of a split was given (`LayerSplit::describe`), and is empty otherwise.
  - `checkpoint_kv_tokens` is the KV tokens a server's fitted checkpoint slots took from its budget (`PlacedModel`), which `serve` prints as it starts, and `kv_kept_context` why its automatic budget kept the model's context, which it prints too.
  - `unpaced` and `pipelined_split` are the placement's reasons for its pacing mode (`PlacedModel`), which `serve` resolves its pacing from.
  - `drafter` is what the drafter file given beside the model is (`spec::DrafterKind`, [pair](inference-pair.md)), when one was given.
  - `times` is the load's `LoadTimes`.
  - `host` is a direct load's copy of each file, laid out as the file, for the weights a host reads in place (`core::HostPages::reserved`), which the host reads in place of the payload; it is declared before `model`, which reads it.
  - `model` is the placed `Model`. It is declared last, so it is destroyed before the bytes it reads.
  - A `LoadedModel` is built in place by `load_model` and is never copied or moved, since a host backend keeps addresses in the file's payload or in `host`.
- `planning_adopt` gives a tensor group's member its shard as storage of its own on every backend (`Backend::alloc_weight`), recorded as an upload with its description (`shard::Held`) and streamed into, or in a mapped load written from the mapping there and then; it sizes its records for each tensor once whole and once as a shard on each backend.
  Until the hook returns, the shard's storage is its alone, so a write that fails drains the backend (`sync`) before the storage goes with the error.
  A shard's zero runs (`shard::zero_runs`) are written there and then in every load mode, so no storage is trusted to hold zeros; the stream and a mapped load write its file runs as `put_runs` gives them.
- `WeightPlan { host_reads, uploads }`: what the loader's hook records while the model is built: per tensor whether a backend that reads in place took it, and each `Upload { tensor, backend, buffer, shard }`, a weight a copying backend took; a tensor group's member takes only its shard, the copy `shard` describes ([shard](model-shard.md)), and without one the whole tensor.
- `planning_adopt(weights, backends, plan, defer) -> AdoptWeight`: the adoption hook `load_model` builds the model with, over the file's `ModelWeights`. A backend that reads in place (`Backend::reads_in_place`) adopts the weight where it lies and `host_reads[i]` is set. A backend that copies adopts it there and then unless `defer`; with `defer`, as the streamed modes `auto` and `direct` build, it gets storage that is not filled yet (`Backend::alloc_weight`), recorded as an upload. The model hands each tensor to each backend at most once, and `plan` is sized for that before the model is built, so recording cannot fail while a buffer is held. `model-validation` checks what it records in both ways.
- `detail::plan_pieces(tensors, spans, file_of, granules, limit)`: the reads of a streamed load, for the weights the devices copy and, in `direct`, for a host's copy. Each `Piece` reads whole granules of one file (`format::FileReader::granule`) from a granule boundary, at most `limit` bytes rounded down to whole granules, and carries on over the tensors that follow in the same file while no gap between them is longer than a granule; its parts say which bytes of which tensor it holds and where.
- `detail::reads_around(streamed, available)`: whether `auto` reads around the file cache, which it does when the bytes it streams are more than the host's available memory, since they would be evicted before they were uploaded; with no figure for the memory it does not.
- `detail::open_reader(path, around)`: a reader for one file, direct when `around` asks and the file system takes direct reads, and through the cache otherwise.
- `detail::stream(pieces, readers, destinations, streamed, times)`: the read ring ([read_ring](inference-read_ring.md)) reads the pieces on up to eight reader threads into up to sixteen slots (`detail::kStreamReaders`, `detail::kStreamSlots`), fewer for a load with fewer pieces, and a piece with `into` straight there instead; and the calling thread sends each part to every upload of its tensor (`destinations`), to an upload with runs only the bytes its runs hold, each to its offset there, and, once a piece is sent, reports the bytes of its parts to `streamed`.
  `put_runs` sends a part's bytes a member holds: runs shorter than a page each, the rows of an expert stack's column shard, packed on the host and written in one write for as long as they follow one another in the storage, which a shard's zero rows interrupt, since a device copy a run costs far more than a few hundred bytes, and longer runs copied or written run by run; a mapped load writes a member's shard from the mapping the same way.
  A backend that wraps the ring's slots (`Backend::wrap_host`) takes each part of a slot as one device copy out of it, the copies of a piece submitted together, and the slot goes back to the readers once they retire: the thread waits for the piece before the one it has just queued, so the device copies one piece while the next is queued. Any other backend, and every part of an `into` piece, gets a `write`, which consumes its source at once. `LoadTimes::copied` counts the bytes copied straight out of the ring. A read that comes up short of a part stops it with "`<path>` ended at N bytes, before its tensors", since the file was cut after its header was read. Whatever fails, a read on a reader thread, a copy, a write or the callback, the readers are stopped, every backend the stream sends parts to drained, so no copy still reads the ring, and the readers joined as the ring is freed, before the error goes on.
- Lookup source preparation: after the architecture has declared its lookup roles, `detail::load_weights` makes a `WeightRows` candidate from that tensor's exact `GGUFModel::span` and a shared `FileReader`, then passes candidates to `plan_placement` before it materializes a full host table. Placement validates the role and tensor metadata and records one selected policy per candidate. `device` leaves the full tensor on the ordinary adoption/upload path. `file` attaches the candidate's `WeightRows` source, over a buffered reader in `automatic` and `mapped` and a direct one in `direct`, and does not adopt, stream, map or warm the table; the tensor's full-data pointer is cleared and its rows are read on the table's readers in every mode.
- `load_model(path, backends, request, options = {}, report = {}, mode = LoadMode{}, drafter_file = {}) -> unique_ptr<LoadedModel>`: it reports `metadata` as it begins, `fit` before the placement is planned, `allocate` before the model is built (`place_model`'s `fitted`, or `construct_model` after a lookup table's `plan_placement`) and the weights' bytes in `weights`, which a mapped load warms before the allocation.
  A `drafter_file` is read to its headers and paired with the model first (`spec::pair`): MTP blocks are joined to the model (`spec::join_blocks`) and loaded as its embedded drafter, mapped or streamed from their own file as the model's tensors are; a draft model is left for the caller to load as a model of its own.
  1. It reads the headers of the file, or of every shard of a set, with `gguf::read_gguf`, and asks the placement whether a host will read weights in place (`infer::host_reads_in_place`): one of `backends`, or the CPU backend the placement adds for experts on the CPU (`PlacementRequest::cpu_moe`). It also plans the architecture metadata to find declared lookup roles and makes bounded candidates from their file spans. `direct` opens every file for direct reads, and a system or file system that does not take them is refused with the reader's reason ("--load-mode direct: `<path>` is on a file system that does not take direct reads"), before anything is built.
     Every reader a load opens, here or in step 6, checks its file's size against the header's (`gguf::check_size`), as the mapping does, so a file whose size changed since its header was read is refused; a rewrite that keeps the size is not detected.
  2. `mapped` maps the payload (`gguf::map_payload`) after lookup placement, then warms tensors in file order, reporting their bytes to `progress` (`gguf::warm`, whose page-sized stride does not guarantee touching every page of an unaligned tensor). A disk-resident lookup is excluded from this whole-tensor warm. Pages read in stay resident only while the host can hold them, so when the set being warmed is larger than host available memory (`core::host_memory_available`) it is not read in: its pages would be evicted before a device copied them and read from disk twice, so they are left for whoever reads them to read once, and the progress reports 0 and then the total being warmed.
     `auto` maps the payload only when a host will read ordinary weights in place; otherwise it reads nothing yet. `direct` maps nothing.
  3. It builds the tokenizer and the chat format.
  4. It takes the file's weights (`infer::gguf_weights`, an `infer::ModelWeights`, in the registry, which chooses the module by `general.architecture`: qwen3, qwen3moe, qwen35, qwen35moe or qwen4exp, a missing key read as qwen3 and another name refused), which reads the architecture's configuration once and checks the tensor table; a view's data is null while its file is not mapped.
     `direct`, when a host will read ordinary weights in place, then reserves a copy of each file laid out as the file (`LoadedModel::host`), as long as its header gives it and rounded up to its reads' granule, and points every view there, so the host adopts addresses whose offset within a page is the mapping's. Nothing of the copy has memory yet, and the host reads none of it before step 6 fills it, since a backend that reads in place does not read a weight as it adopts it.
  5. It places the model over `backends` as `request` asks, with `options`' caches (`infer::place_model`), through `planning_adopt`, deferring the copies in `auto` and `direct`. For lookup candidates, `auto` keeps a table on the layer's backend where the split still fits the fitted KV budget and otherwise reads it from the file; `device` fits the KV budget beside the whole table or refuses. This choice is independent of `LoadMode`. Before adopting or allocating weights, the runtime checks their types (`Backend::supports_type`) and the ops the plan names (`Backend::implements`) on their home backends, and decides which host expert layers can stream to their mixer devices, a destination lacking a type or an op keeping the layer at home. When it returns the model roles have been checked, weight storage allocated and cache storage constructed with its budgets, so in those modes a missing tensor or a rejected cache budget fails before any weight is read. Physical KV backing and execution scratch grow as needed later and can still fail to allocate.
     Building first and copying after costs `mapped` the overlap of the copies with the allocations, which measured 3.6 percent on a warm Qwen3-8B load on the Radeon VII, so `mapped` keeps copying as it builds; the streamed modes overlap their copies with their reads instead.
  6. `mapped` has copied every weight already, as the model resolved it: construction adopts it through a copying backend straight from the mapping.
     The streamed modes sort ordinary weights three ways: those a host reads in place, which `direct` reads into its copy; the rest a device copies, which both stream; and in `auto` those a host alone reads, whose pages are read in after the stream. A host-resident lookup participates in host lifetime and warming, while a disk-resident lookup is excluded from the whole-tensor stream and mapped warming; its requested packed rows are read later through its bounded source. A device-resident lookup follows the ordinary full-tensor copy or host-read path.
     `direct` refuses when the weights a host reads are more than the host's available memory ("--load-mode direct: the host reads X GiB of weights in place and has Y GiB available; auto and mapped map them instead"), before a byte is read. Otherwise it commits the ranges of its copy those weights' reads cover, refusing a commit the system turns down with the same advice, and reads them straight there, in one pass front to back over each file with the pieces the devices take, all around the file cache. A device that also takes one of those weights, as the head of a tied embedding split between the CPU and a device does, is written from the host's copy, so each weight is read once.
     `auto` opens a file for direct reads when the bytes it streams are more than the host's available memory (`detail::reads_around`) and the file system takes them, and through the cache otherwise (`detail::open_reader`).
     Both report 0, plan their reads (`detail::plan_pieces`, 16 MiB) and stream them on up to eight reader threads (`detail::stream`): one or two readers of 16 or 32 MiB measured fastest on the loader's first hosts, and on a pool of SATA SSDs whose 16 KiB records stripe a read over four disks in 4 KiB pieces eight readers of 16 MiB read 1064 MB/s where two read 500 (docs/STATUS.md, Server startup profiled end to end).
     `direct` then gives back the pages of its copy that hold none of the host's weights (`HostPages::decommit`), which whole-granule reads and the gaps they read through brought in, keeping the page after each weight, as a mapping's next page is there to read.
     `auto` then reads in the pages of the weights a host alone reads, under the same host-memory rule applied to their bytes. On the CPU alone nothing is copied, so the load reads in the pages of every tensor the model takes, as `mapped` does, after the model is built rather than before.
     The progress counts the bytes of every tensor some backend took, each once, and reaches complete after the last of them.
  7. When no host reads a weight in place, which is the case for a model on device backends alone, it releases the host's copy of the weights (`GGUFModel::release_payload`, and `host` for a direct load), which `auto` never mapped. Otherwise it lets the pages of every tensor no host reads leave the host's working set (`GGUFModel::drop_pages`), as with experts on the CPU beside a device.

The caller makes the backends (`backend::make_backends`) and builds the request and options from its own flags, so a device that cannot be opened, or a malformed device list, fails before the file is read.
The caller also renders the progress: the CLI prints "Reading model metadata..." before the call, and its bar prints "Preparing model..." once, when the progress is complete.
Worker counts stay the caller's (`Model::set_threads`).

A failure anywhere in the sequence throws and frees what was built.
A model whose construction failed has already drained its backends (`model/runtime.hpp`), and one whose stream failed drains them as it is destroyed, before any buffer is freed; `load-progress` checks both a failed write and a failed progress callback on a backend whose uploads stay outstanding until it drains.
