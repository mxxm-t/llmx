# `src/quant/nvfp4.hpp` - NVFP4 software decoding

GGUF type 40 holds 64 values in 36 bytes. Four unsigned E4M3 scale bytes precede four groups of eight packed bytes. Each group takes low nibbles for its first eight values and high nibbles for its last eight. `nvfp4_scale` supplies half the scale for the doubled E2M1 `FP4_VALUES` codebook owned by [`quant/fp4.hpp`](quant-fp4.md); reserved scale 127 gives zero. CPU and Vulkan read-only support uses software decoding, not native FP4 hardware acceleration. The tested model scope and landing status are recorded in [STATUS](../STATUS.md).

The CPU registry owns row decoding. Vulkan uses the software decoder for embedding and row/tile products, and the shared weight-scale owner carries global scalar or per-expert scales. Independent raw and operator checks cover the code mapping, scales, grouped products and routing. Their scope and the model-level evidence are summarized in STATUS.

Vulkan devices with the required float controls can use F16-rounded tile inputs, widened for F32 products and sums; other devices use F32 tile inputs. Shared kernel and module owners declare and check the needed controls. This changes activation input rounding, not packed weights or software decoding. Device and model qualification are summarized in STATUS.

The independent seed-12345 HF producer refused near-tied MoE routing before any candidate comparison. The first stable seed, 12346, gives routing margin 0.000899821240474268 above 0.0001; ordinary/split references and 60 prospective calibration runs are complete (30 accepted each for F16/BF16), freezing only the new family. The original fixtures have no `.scale` sidecars; the exact-equivalent extensions below exercise them without changing the reference. The researched older released file uses 40-byte blocks across all 252 tensor spans and is incompatible with this 36-byte layout. A current-36-byte Qwen3.5-0.8B released file has global F32 sidecars that must be included. [Initial reference and layout evidence](../benchmarks/nvfp4-first-checkpoint-20261025.json).

## Released weight scale sidecars

The modern 36-byte blocks are only the local block component of a weight. Current producer files also carry F32 `<stem>.scale` beside `<stem>.weight`, scalar for dense matrices or indexed per expert; it must multiply the decoded weight exactly once. The [producer contract](https://github.com/michaelw9999/advanced-gguf-quantizer/blob/main/docs/advanced-gguf-quantizer-nvfp4-contract.md) and [NVIDIA reconstruction description](https://docs.nvidia.com/deeplearning/transformer-engine/features/low_precision_training/nvfp4/nvfp4.html) distinguish this global scale from per-16-value block scales. Bounded reads of three pinned releases confirm nonidentity sidecars. The 0.8B Qwen3.5 candidate has current 36-byte geometry, but block decoding alone is insufficient to run it correctly.

The inspected mx W4A16 graph applies `.scale` after dense/expert products and does not consume `.input_scale`; this observation does not generalize to activation-quantized NVFP4 paths. Generic scale association is implemented in [weight_scales](format-weight_scales.md), carried by `TensorView.scale` and `Weight.operand()` into backend `WeightView`. Model validation, fit, adoption and streaming retain scalar/per-expert scale storage. CPU and Vulkan embedding and all six matrix entry points apply it through their shared owners. The fused Vulkan `moe_step` also carries `WeightView` operands and checks their scales before specialized dispatch. No NVFP4 fused build is registered, so NVFP4 routed calls use the base step, which forwards the same views through the ordinary matrix owners. Independent operator/model and Python reference/raw-conversion checks cover scalar, expert and sharded scales, including dtype, overflow and pre-write refusal cases. The exact-equivalent scalar/expert extension below covers both CPU and Vulkan consumers. Released-file qualification progress is recorded in STATUS. Detailed pins, descriptor offsets and bounded reads are retained in `build-nvfp4-research/provenance.md`.

## Exact-equivalent scale fixtures

`tests/nvfp4.py` first checks the original config, decoded and packed hashes, then repacks positive scalar/per-expert gains 0.5/0.25 and independently proves that effective F32 bytes are unchanged. It reports the new packed hash. The shared harness consumes original and scaled fixtures together (300 full-logit and 24 NLL comparisons), reusing unchanged HF goldens and frozen bounds. CPU F32 passes with maximum logit/NLL errors 1.80e-6/1.3e-7; Vulkan F32 also passes 300/24 with maximum logit/NLL errors 1.27e-6/6e-8. This is fixture-identity reuse, not new calibration or released-model acceptance.

The Vulkan F16 request also passes all 300/24 cases through its wider F32 fallback at the F32 bounds. Vulkan BF16 passes all 300/24 with maximum logit/NLL errors 0.00811158/0.00038393 against the unchanged 0.04395330/0.00461681 limits.

Model scale tests cover routed layers, layer/TP2 placement and streamed scale adoption. The initial released MI50 smoke established execution only. The [historical early screen and profile](../benchmarks/nvfp4-early-vulkan-screen-20261025.json) used mismatched mx build inputs and is not the current performance comparison. Current model and performance evidence is recorded in STATUS.
