# `src/server/` - the multi-user server

`llmx serve`, in five headers above the inference layer, designed in
`docs/SERVER.md`. No external libraries: sockets, HTTP/1.1, JSON and the
scheduler are the runtime's own.

- `http.hpp`: `Listener`, `Connection`, `Request`.
  Blocking BSD or Winsock sockets for the connections, one thread each; a request is read with size limits (413 and 431 past them, 400 for a malformed line), a reply is written whole or as a chunked stream, and a client's disconnect surfaces as a failed write, which throws `ClientGone`, rather than a signal.
  `peer_closed` asks without writing, blocking or taking a byte whether the client has closed the connection: `poll` or `WSAPoll` with no wait, then a one-byte `MSG_PEEK` (with `MSG_DONTWAIT` where the platform has it) whose end of stream or reset means closed and whose data means open, so a client that shuts only its sending side reads as closed.
  On Windows the poll asks for normal data only (`POLLRDNORM`), since its `POLLIN` also takes urgent (out-of-band) data, and the peek there, which has no `MSG_DONTWAIT`, would then wait for normal data that may never come.
  The listening socket is non-blocking: `Listener::accept` polls it, looking for `close()` every 100 ms (`kCloseCheckMs`), and holds the listener's mutex while it does, so `close()`, from any thread, closes the socket only once no accept uses it, and an accept never reads a socket that is closed or that a new one has taken the place of.
  `close()` therefore takes up to 100 ms while an accept waits for a client, and the accept loop wakes every 100 ms while no client comes; a client that arrives is taken at once.
  `accept` returns no connection only once `close()` has been called, and any other failure is retried: at once when it is one client's (a connection aborted before it was taken, an interrupted call) or says only that no client was waiting after all, and after 50 ms otherwise, so a client's aborted connection never stops the server and an error that persists cannot spin a core.
  The connection it returns is made blocking, since macOS and Winsock hand it the listener's non-blocking mode, where Linux does not.
  `respond` throws while a stream is open, since a second head would land inside the chunked body.
  The `http` CTest drives it with its own client.
- `scheduler.hpp`: `Request`, `Scheduler` and `SampleParams`.
  `SampleParams` is `infer::Sampling` (`inference/sampler.hpp`), with its defaults and ranges, plus what only a request has: a list of stop texts, `until_limit`, a request without a cap, and `logprobs` and `top_logprobs`, the log-probabilities it asks for.
  A request's token is drawn from its row of the pass's mapped logits, read in place, through `infer::sample(row, width, params, eos_id, ...)`, the call `infer::generate` makes, so `ignore_eos` masks the end of text here as it does in the CLI.
  Connection threads submit requests and drain their token channels; the scheduler thread is the only thread that calls the model, pushes to the channels and keeps the ledger.
  It owns a `SamplingPool` of `kSamplers` (4) threads, or one fewer than the CPUs the process may use (`core::automatic_threads`) where that is fewer, which draw a retiring pass's rows beside it (`Stats::samplers`, printed as the server starts).
  It runs rounds over the model's pass API (`docs/SERVER.md`, The round) in one context it reserves as it is made (`Model::reserve_passes`) for its passes in flight, of every decoding request's row and a ubatch of other rows each, a logits row for each request at most: one per stage on a pipelined split (`Model::pipelined`, `stage_count`) and one elsewhere, or the `passes` it is given, which it refuses above one on a placement that is not pipelined; a reservation the memory cannot hold drops a pass at a time, with a line on stderr.
  A `Slot` records the pass in flight in it, its requests by entry with the history each had and the rows each adds, those it samples, the run of logits rows it took with `take_rows` and its decode entries.
  Each round records the device stages `round_steps` gives (`advance`, through `run_pass_stage`), retires the passes it names (`retire`: `pass_logits` for each wanting row, the draws, the tokens pushed in entry order, `end_pass`, and the rows resumes recomputed), ends the cancelled requests no pass holds, and, while a slot is free, makes room and forms passes (`form`: `begin_pass` and its first stage), then records the round's stages on the host (`Model::stage_on_host`), which compute as they are recorded.
  `form` takes decode entries up to `decode_share` of the decoding requests, those in flight counted, the requests that left flight earliest first (`landed_`, the formation order of the pass each last left), and skips a request in flight or stalled, so however requests arrived the passes carry about as many decode rows each.
  A stage that fails has already abandoned its pass in the model, a failure while a pass's logits are read or its rows drawn abandons it (`abort_pass`), and either way that pass's requests end with the error and give their blocks back (`fail_pass`) while the other passes in flight go on; a round the scheduler's own rules cannot go on with abandons every pass and ends every active request (`fail_all`), and `run` abandons every pass in flight (`abort_all`) before it ends everything at a stop.
  A request cancelled in flight is not sampled in `retire`, and ends once its pass has retired, its history kept as a donor.
  `Request::next` waits for a token or the end only until a deadline, so a connection thread can look at its client between tokens.
  The channel carries a `Request::Token`: the sampled id and, for a request that asks (`SampleParams::logprobs` and `top_logprobs`), its log-probability and the most likely tokens at its position, most likely first.
  `retire` gives each wanting row whose request was not cancelled to the pool as a `Draw`, the request and its row of the pass's mapped logits, which `draw` reads in place on whichever thread takes it: the id with the request's own settings, history and generator, and, for a request that asks for log-probabilities, a copy of the row, or, once its reader has fallen behind, the values themselves; `step` then pushes each token in entry order on the scheduler thread and ends the request on EOS, a stop string or its limit.
  A draw touches only its own `Draw`, its request's generator and its request's row copy, and a request wants one row a pass, so no draw depends on another or on which thread took it, and `SamplingPool::run` returns only once every draw has, before `end_pass` gives the pass's logits rows back.
  They come from the logits row `sample` reads, before the penalty, the temperature, top-k and top-p: for a request that asks, `step` moves the draw's copy of that row into the token, the one copy a row gets, and `next` turns it into the values with `inference/logprobs.hpp` in the thread that reads the channel, so the scheduler's passes do not wait for a walk over the vocabulary; a C++ test reads them from the channel as the routes do.
  A reader can fall behind, as a connection thread does while a client that stops reading holds its write: once `kRowsWaiting` (8) tokens wait with their rows (`rows_waiting`, which `retire` reads before it hands the rows to the pool), the draw computes the next token's values itself from the row in place with the same `fill`, and `step` sends them without a row, so a request holds at most that many rows on its channel and two more in all, however long its reply.
  `next` hands each row it has finished with back to the request, and `push` gives one to `step` in place of the row it moved out, so the next pass fills it rather than a new allocation; a cancelled request's rows are dropped without their values.
  `next` reads `top_logprobs` from the request's parameters, which nothing changes once the request is made.
  The KV pool holds `--ctx-size` tokens in total, and `submit` owns what one request may hold (`token_limit`): it refuses a prompt plus `max_tokens` past it, or an uncapped prompt that fills it, and sets an uncapped request's `max_tokens` to the room its prompt leaves; past `--max-queue` queued requests a new one is refused with 503, paused requests not counted.
  The scheduler takes `--max-seqs` and `--max-queue` as it is given them, and the CLI refuses either below 1.
  Each round with a free slot gives the growth steps that fall due their room, admits queued requests the pool can hold (a capped request's prompt plus `max_tokens`, an uncapped one's prompt plus a step it grows by as it generates; a paused request's history stays as a donor and it resumes from it), forms a pass (`form`) in each free slot of the ready decoding requests' next tokens up to the decode share (`decode_share`), those that left flight earliest first, then, in order of first admission, a slice of what each other request's cache lacks within one ubatch budget the slices share, samples per request with its own seeded state, and finishes on EOS, a stop string or the token limit.
  A request's prompt and generated tokens are never rewritten, and its cache's length is its progress.
  `classes_` records how each stretch of its history was computed (`RowClass`: the stretch's end and extent, which chooses a device's kernels and a streamed layer's path): from its first admission, a forked prefix as its donor recorded it, the rest of the prompt at the whole prompt's extent, and the generated tokens at extent 1; a donor keeps the classes of what it holds.
  A slice never leaves its stretch and carries that stretch's extent, so a prompt's slice takes the kernels and the path one pass over the prompt would, and a resume recomputes every row the way it was first computed, generated tokens as entries of extent 1, at most `kReplayRows` (64) a request a pass, each costing `ubatch / kReplayRows` of the budget, at least one.
  A pause leaves the request's history as a donor whose id the request keeps (`donor_`), even short of a full block; resumed, the request takes that donor back whole if it is still there (`own_donor`), so it recomputes nothing, and `Stats::taken_back` counts those resumes.
  Otherwise `best_donor` matches it by tokens and classes (`alike`), so a resume forks only rows computed as its own were, and a first admission by tokens alone; the pass that ends a request's history wants its logits.
  Each finished request's log line counts its pauses, the resumes that took its donor back and the rows its resumes recomputed.
  A finished request's history stays as a donor: a later prompt repeating its tokens forks the shared full blocks and prefills only the rest.
  A model whose layers keep a recurrent state (`Model::keeps_state`) keeps no donor (`park`), since its state exists only at the end of what it has read: a finished or paused request gives back its blocks and its state slot, and a paused one resumes by recomputing its history from its start; the scheduler is refused as it is made when `--max-seqs` passes the model's state slots (`Model::state_slots`), so admission never waits on a slot.
  The donor a request forks is chosen before room is made and the other donors go first; if the pool is still short the chosen one is consumed: only the shared blocks pass to the request and the rest are freed, so shared blocks are reserved once and a follow-up turn keeps the history it repeats.
  A request sharing every full block of its donor, a follow-up turn or a resume, consumes it before any other donor goes, so an unrelated donor stays whenever consuming that one makes room.
  `make_room` (in `policy.hpp`) is the one owner of who gives up blocks for whom.
  `enter` admits a queued or paused request with it and `grow` gives growing requests their steps with it, the earliest admitted first, before anything is admitted in the same round; a request it cannot give a step to sits out the pass (`stalled_`), keeping its cache, and nothing resumes or is admitted while one does.
  The admission number is set at a request's first admission and never renewed, and `active` and the paused requests (`paused_`, the scheduler thread's, outside `--max-queue`) are kept in its order; paused requests resume oldest first and stop at the first that does not fit, and the queue is admitted only once none is paused.
  `Stats` and `/v1/health` count `paused`, `stalls`, `waits` (the stalls whose plan waited on a request in flight), `recomputed` and `taken_back` beside `pauses`, and `passes` and `in_flight`, the passes kept in flight at most and now; `Stats` also gives the ledger per pool (`reserved`) beside the blocks the donors hold (`donor_blocks`), and the `server-passes` CTest runs these rules' round over the policy core under a simulated executor, the round `run` takes at any number of slots.
  A `timed` scheduler (`serve --timing`) keeps a `Timing`: its rounds and their time, the thread's time in them recording, relaying, sampling and forming passes (`assembly_ms`), and where it was held, apart, from the backends' `host_times` around each stage and its own clock around each logits read; and each stage's device time over the span its readings cover, with the rows the passes retired in it carried, read every 32 rounds (`end_round`) from `device_ms` on a device and from the thread's own time on the host.
  `on_retire`, when set before `run`, gets each pass as it retires, before its rows are sampled (`Retired`: each entry's request, the history it found, its rows, extent and want, and a copy of each wanting row), so a test can replay the passes through `Model::forward`.
  The `server-resume` CTest drives the scheduler directly with the synthetic Q8_0 model and reads the values from the channels, a paused request's against its run alone, and on one to three CPU stages cancels a request and stops the scheduler from inside a pass's stage; the `server-passes-cpu` CTest runs it on one to three CPUs at P = 1, S, S + 1 and 2S, every reply its reply alone on one CPU at one pass, with pauses, a plan waiting on a request in flight, a cancel, a failure and a stop from inside a stage, and replays each run's passes through `forward`.
  A pass that finds no logits rows fails the round (`fail_all`) at any number of passes in flight, and one that `form` builds empty fails it only with nothing in flight: the oldest request sits a pass out only while a capped request holds room, so that happens only if a rule were broken, and failing keeps the loop from spinning; with passes in flight `form` stops at a free slot no request has rows for.
  Cancellation is a flag seen at the next round, which ends a queued or paused request wherever it waits (`leave`, which drops a paused request's own donor when it holds less than a block) and an active one once no pass in flight holds it, its history kept as a donor; blocks return once the device has retired the pass that read them.
- `sampling_pool.hpp`: `SamplingPool`, the scheduler's sampling threads.
  `run(n, job)` runs `job(i)` for every index below `n` on its threads and the calling thread, each index once, taken under one mutex as a thread comes free, and returns once every call has returned, rethrowing the first exception a call threw only then, so a job's captures outlive every call; a single index runs on the calling thread without waking a thread.
  The pool decides nothing: which request's row an index names, and what a draw may touch, are the scheduler's.
  The `sampling-pool` CTest runs it with no thread and with one, three and four.
- `policy.hpp`: the scheduler's policy core, free functions over plain data that the scheduler calls with its requests and passes and the `server-passes` CTest with a simulated executor's.
  `Pools` holds each cache pool's blocks and the tokens a block holds, and `blocks_for` counts what positions take in each, never more than the pool.
  `Growth` is the one owner of what a request reserves: `entry` at an admission, a capped request's history and what it may still generate or an uncapped one's history and `tokens` more, and `step`, the blocks an uncapped decoding request adds before a pass once its next position would pass what it holds, reaching `tokens` past that position; both read the same `tokens`, so the first uncapped request a growth plan pauses frees a whole step and a plan never pauses more than one.
  `make_room`, over the ledger (each pool's blocks and what is reserved, each donor's blocks, and each running request as a `Holder`: its first admission, whether it is uncapped, its reservation, what its donor would keep and whether a pass in flight holds it), is the one owner of who gives up blocks for whom: donors oldest first, the forked one last or first, then, only for a request that grows, uncapped requests admitted after it, latest first, each one's headroom and then, if short, its donor; it returns what it takes (`Taken`) only when that is enough, and with `wait` set when a request it would pause is in flight, in which case the caller takes nothing and plans again at its next room.
  `round_steps` takes each slot as a `Flight` (whether a pass is in flight in it, its formation order and the stages recorded) and gives the round's `Steps`: from the last stage down to stage 1 the oldest pass waiting for each stage, and the passes whose last stage an earlier round recorded, oldest first.
  `decode_share` is the most decode entries a new pass takes, the decoding requests, those in flight included, over the passes rounded up, once the passes fill the stages, since then a pass retires every round and a request held back joins the next; with fewer passes than stages, every ready one.
  `LogitRows` holds the runs of a reserved context's logits rows the passes in flight took, oldest first: `take_rows` takes a run after the newest one, or from row 0 when that does not fit, and gives `size` when none fits; `give_rows` gives one back, and runs come back oldest first, so a run given back early, an aborted pass's, waits for the runs taken before it.
  A run always fits while it and the runs held want at most half the rows, and, at one pass in flight, all of them; `logit_rows` sizes a context's rows at twice what its passes in flight may want together, or once that at one pass.
- `api.hpp`: the routes and `serve(model, tok, format, config, listener)`.
  `Config` carries the scheduler's `passes` and `timing` beside its queue and sequence limits, and `serve` prints the passes the scheduler keeps in flight as it starts.
  `/v1/health` adds a timed scheduler's figures as `timing` (`timing_json`): each time a mean over the rounds, each stage's idle share over the span its device time was read in, and the device-bound rate, the rows the passes carried over the busiest stage's device time.
  Native `/v1/generate`, `/v1/chat` and `/v1/health`; the OpenAI-compatible `/v1/chat/completions`, `/v1/completions` and `/v1/models`, one parse, one request and one drain loop shared with the native routes, with the clients' synonyms accepted and errors in their shape.
  Every POST route reads its body through `body_of`, which refuses anything but a JSON object with 400.
  `encode` gives a prompt's ids to the generating routes and `/v1/tokenize` alike, refusing a text the tokenizer cannot encode with 400.
  The native `/v1/tokenize` and `/v1/detokenize` answer on the connection thread without the scheduler: `tokenize` encodes a `text`, or `messages` rendered by `render_messages` as the chat routes render them, and adds no start or end token, since no route adds one to a prompt, so it does not read `add_special`; `detokenize` reads each id through `integer_value`, from 0 to the tokenizer's last id, and passes the decoded bytes through `utf8_sanitize`, which gives a whole reply's ids back as its text.
  The path of a generating route resolves to its `Route` once, and `compat(Route)` alone says which of those routes speak the clients' shape, so a compatible request refused while it is read gets that shape too.
  `integer_value` refuses a number that is fractional or outside what it is cast to with 400 before any cast, for the fields `integer` reads (`max_tokens`, `max_completion_tokens` and `n` within `int`, `seed` from 0 to below 2^64) and for each id `detokenize` reads.
  The sampling fields start from the defaults of `infer::Sampling` and take the ranges it holds beside them, the ones the CLI's flags take, so a value the CLI refuses the server refuses too, apart from a `top_k` of -1 on the compatible routes: `setting` refuses `temperature`, `top_p` and `penalty` (or `repetition_penalty`) with 400 outside `Sampling::temp_range`, `top_p_range` and `penalty_range`, checked on the float the sampler reads, and `integer` refuses `top_k` outside `top_k_range`.
  On the compatible routes an absent `max_tokens`, or -1, means no cap (`until_limit`): the reply may run to the end of the request's context; the native routes keep a default of 64 and refuse -1 as any other cap below 1.
  A `seed` of -1, which clients send for a random one, is no seed on the compatible routes, sampled as a request with none is, and the native routes refuse it as any other seed below 0.
  A `top_k` of -1, which clients send for no top-k, is 0 on the compatible routes, which keeps every token, and the native routes refuse it as any other `top_k` below 0.
  `boolean` reads `ignore_eos` on every route, `false` when absent, and refuses with 400 any value other than `true` or `false`, where `stream` and `include_usage` still read anything but `true` as false.
  The routes only map the scheduler's refusals to statuses.
  `Api` holds the `chat::ChatFormat` that `serve()` is given, the opened model's, whose refusal `cmd_serve` raises before the listener opens.
  `messages_of` reads a chat request's messages as `chat` records its turns: a message's `reasoning_content` as given when it is a string, and otherwise, absent or null, an assistant message through `chat::ChatFormat::assistant`, the owner `chat` records its replies through; a `reasoning_content` of another type is refused with 400.
  A render the template itself fails, its `raise_exception` included, is refused with 400 and the template's message.
  Log-probabilities come in each route's shape (`docs/SERVER.md`, Log-probabilities): the completions route reads `logprobs` as the count of most likely tokens to list, from 0 to 20 (`kTopLogprobs`), and the other routes read `logprobs` true or false and `top_logprobs` from 0 to 20, refusing a `top_logprobs` above 0 without `logprobs`; `given` treats a null field as absent and `boolean` refuses a field that is neither true nor false.
  A token's text in those shapes is `token_text`: its bytes when they are whole UTF-8, else `bytes:` and each byte as `\xNN`.
  Every value is written by `jmini::number`, the shortest decimal that reads back as the same float, and a reply that does not ask carries no byte of them.
  The native shape keeps `number`'s `null` for a value JSON cannot hold; the compatible shapes type the field as a number, so `compat_number`, a free function beside `error_json`, writes -9999 (`kLogprobFloor`) for a value below it, minus infinity or a NaN, which `server-utf8` checks.
  The chat route's `logprobs` object carries `"refusal": null` beside `content`, as its schema lists.
  The drain loop cancels a request when a write to its client fails, and between writes looks at the socket every 100 ms (`kProbe`), token or not, cancelling once `peer_closed` says the client has gone, so a client that leaves while its request is queued, prefilling or building a whole reply is noticed within about 100 ms as well.
  Either way a `ClientGone` ends the loop, and `handle` answers it with nothing, not even a 500, so the connection just closes.
  The compatible replies carry a `timings` object beside `usage`, and every finished request logs a line on stderr; both take the decode rate from `Request::Timings`.
  A stream whose pass fails ends with one `data:` event holding the error in the route's shape, and no `data: [DONE]`, since its 200 head has gone out.
  The drain loop holds a character split across tokens until its bytes complete (`utf8_complete`, by `utf8::lead_length`), and `utf8_sanitize` writes U+FFFD for each byte where `utf8::valid_length` finds no character, the JSON parser's own rule ([core-utf8.md](core-utf8.md)), so an overlong form, a surrogate or a value above U+10FFFF never reaches a reply.
  The model's name and every error message pass through `utf8_sanitize` too: the name once, as `Api` is built, since it is the model's file name and a Linux file name can hold any bytes, and each message in `error_json`, since a message can carry a chat template's text from the model file or a backend's failure.
  The `server-utf8` CTest checks `utf8_sanitize` on those three and on valid text, `utf8_complete` on characters held back and let through, `error_json` on a message with a stray byte in both shapes, and `compat_number` on values at, below and past the floor; the `server` component names its synthetic model with a byte that is not UTF-8 on Linux.
  `serve()` and `Api` take the model, its tokenizer and its `chat::ChatFormat`, which the loader builds (`infer::load_model`, [load](inference-load.md)), and never the model file.
